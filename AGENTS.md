# AGENTS.md

## Overview

Обучающий проект: визуализатор алгоритмов на Go. Три независимых слоя:

- `algorithms/` — библиотека алгоритмов (чистый Go, без UI);
- `visual/` — визуализатор: Go-сервер (SSE, кадры) + TS-фронтенд (Vite);
- `quiz/` — CLI-квиз по учебной программе.

Канонический язык проекта — `GLOSSARY.md`, принятые решения — `docs/adr/`, требования — `docs/SPEC.md`, план — `PLAN.md`. Читай их перед работой; новые термины и решения фиксируй там же.

## Commands

- Build: `go build ./...`
- Vet: `go vet ./...`
- Test (все): `go test ./...`
- Run visualizer: `go run ./cmd/web` (после появления)
- Run quiz: `go run ./cmd/quiz` (после появления)
- Frontend: Vite в `visual/` (после появления; build output — `dist/`)

## Conventions

- Библиотека `algorithms/` **не импортирует** `visual/` и `quiz/` — жёсткая граница слоёв (ADR-0001).
- Алгоритмы работают в quiet mode (обычная функция) и опционально принимают Emitter для событий шагов (ADR-0001).
- Визуализация строится на кадрах-снапшотах (ADR-0002), транспорт — SSE (ADR-0003).
- Комментарии и UI-тексты — на русском; идентификаторы и имена пакетов — на английском.
- Тесты — на трёх швах: публичный API алгоритмов, SSE-эндпоинт (кадры), движок квиза. Внутренности не тестируем.
- Процесс: сессия с агентом = один учебный модуль (алгоритм + тесты + визуализация + вопросы квиза + отметка в PROGRESS.md).
- Старый однофайловый `main.go` будет удалён в первом тикете — не расширяй его.

## Git workflow

- **`main` — единственная точка интеграции.** Владелец `main` — основная папка репозитория (не worktree).
- **Один worktree = одна ветка = один тикет**: `git worktree add ../algo-<slug> -b ticket/NN-<slug>`.
- **Агент в worktree имеет право:** коммитить и пушить **только свою ветку тикета** (`ticket/...`).
- **Агент НЕ имеет права:** мержить/пушить в `main`, `push --force`, удалять ветки, коммитить чужие файлы. Интеграция — решение человека.
- **Слияние — из основной папки или через PR на GitHub**, никогда из worktree тикета. После мержа: `git worktree remove`, ветку удалить.
- Перед стартом нового тикета — `git pull` в основной папке, ветка от свежего `main`.
- Если в процессе нужна свежая `main` внутри своей ветки — `git merge main` в своей ветке, не наоборот.

## Review process

- После реализации тикета — ревью по скиллу `code-review`, две оси (Standards + Spec) параллельными субагентами. Фиксированная точка — `main...HEAD` своей ветки (или `main...origin/ticket/...` для ревью чужой ветки).
- Хороший паттерн: **автор кодит в своей сессии, ревью запускается из отдельной чистой сессии** — свежий контекст ловит то, что автор пропустил. Ревьюер не правит чужой код — находки передаются автору.
- **Повторное ревью после фиксов** — только дельта: `git diff <sha-до-фиксов>...HEAD`, без полного прогона. Приоритет перепроверки — поведенческие баги; фикс поведенческого бага обязан идти с регрессионным тестом — тест и есть доказательство.
- Полный повторный прогон двух осей — только если фиксы переписали значительную часть дифа (грубо >30%) или первое ревью нашло архитектурную проблему.
- Запахи из ревью — judgement calls: автор вправе отклонить с объяснением; нарушения документированных стандартов — не вправе.
