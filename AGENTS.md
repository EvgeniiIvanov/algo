# AGENTS.md

## Overview

Обучающий проект: визуализатор алгоритмов на Go. Три независимых слоя:

- `algorithms/` — библиотека алгоритмов (чистый Go, без UI);
- `visual/` — визуализатор: Go-сервер (SSE, кадры) + TS-фронтенд (Vite);
- `quiz/` — CLI-квиз по учебной программе.

Канонический язык проекта — `GLOSSARY.md`, принятые решения — `docs/adr/`, требования — `docs/SPEC.md`, план — `PLAN.md`, сценарии процессов — `docs/WORKFLOWS.md`. Читай их перед работой; новые термины и решения фиксируй там же.

## Context задачи

- Каждая сессия агента всегда начинается с `AGENTS.md` и `docs/WORKFLOWS.md` — это обязательный минимум.
- Для тикетной работы далее читай тикет (`docs/tickets/NN-slug.md`) и релевантную часть `docs/SPEC.md` — только для своих тикетов, не для всего плана.
- ADR и `GLOSSARY.md` — выборочно: читай только записи, относящиеся к задаче, а не весь корпус.

## Commands

- Build: `go build ./...`
- Vet: `go vet ./...`
- Test (все): `go test ./...`
- Test (как в CI, Go + frontend): `make test`
- Run visualizer API: `go run ./cmd/web`
- Run quiz: `go run ./cmd/quiz`
- Frontend dev server: `cd visual/frontend && pnpm dev`; production build: `pnpm build` в `visual/frontend/` (output — `dist/`)

## Conventions

- Библиотека `algorithms/` **не импортирует** `visual/` и `quiz/` — жёсткая граница слоёв (ADR-0001).
- Алгоритмы работают в quiet mode (обычная функция) и опционально принимают Emitter для событий шагов (ADR-0001).
- Визуализация строится на кадрах-снапшотах (ADR-0002), транспорт — SSE (ADR-0003).
- Комментарии и UI-тексты — на русском; идентификаторы и имена пакетов — на английском.
- Тесты — три основных шва: публичный API алгоритмов, SSE-эндпоинт (кадры), движок квиза; для фронтенда визуализатора есть четвёртый публичный шов, описанный в `docs/SPEC.md`. Внутренности ниже этих швов не тестируем.
- Процесс: один worktree/ветка = один вертикальный тикет. Учебный модуль может состоять из нескольких тикетов; его строка в `PROGRESS.md` отмечается после всех обязательных частей (алгоритм, тесты, визуализация, квиз). Тип работы → поток из `docs/WORKFLOWS.md`.
- Изменение зависимостей коммить вместе с обновлённым lockfile (`pnpm-lock.yaml` / `go.sum`); после правок гоняй проверки локально так, как их гоняет CI (`pnpm install --frozen-lockfile`, `golangci-lint run ./...`), иначе его поймает CI, а не ты.

## Process orchestration

- Хост агентов — **только OpenCode** (`opencode.json` + `.opencode/agents/`). VS Code — место, где человек пишет черновики алгоритмов/структур; в автоматизацию он не входит.
- Пользователь общается только с **агентом-оркестратором** (одна сессия = один оркестратор); специализированная работа делегируется **субагентам**, с которыми пользователь не контактирует.
- Оркестратор спавнит только трёх названных субагентов: `implementor`, `reviewer`, `tester` — ограничение зашито нативным правилом `subagent` в секции `permissions` профиля оркестратора (V2); других/общих субагентов не используем.
- Оркестратор строго не реализует и не пишет код: каждое изменение кода делегируется субагенту `implementor`, который работает в worktree тикета (`.opencode/agents/implementor.md`). Оркестратор ведёт только процессные артефакты (статусы тикетов, `PROGRESS.md`).
- Оркестратор управляет потоком из `docs/WORKFLOWS.md`, спавнит субагентов, ведёт статусы тикетов и PROGRESS.md автоматически.
- **Чекпойнты Ч1–Ч4 + Ч2.5** (спека → тикеты → черновик пользователя → находки ревью → мерж): оркестратор останавливается и ждёт явного подтверждения пользователя. Подробности и учебный контракт (черновик алгоритма пишет пользователь) — в `docs/WORKFLOWS.md`.

## Git workflow

- **`main` — единственная точка интеграции.** Владелец `main` — основная папка репозитория (не worktree).
- **Один worktree = одна ветка = один тикет**: `git worktree add ../algo-<slug> -b ticket/NN-<slug>`.
- **Жизненный цикл повторяется на каждый тикет, а не раз на модуль:** worktree → реализация (implementor) → ревью → решение пользователя про мерж → чистка (worktree + ветка) → следующий тикет.
- **Имплементор** перед работой проверяет ветку (`git branch --show-current`) — он обязан быть в **своей** ветке `ticket/...`; проверка ветки — это инструкция, а не нативное ограничение permissions. После прохождения релевантных проверок (`make check` / `go build/vet/test`, `golangci-lint`, для фронтенда `pnpm install --frozen-lockfile` + lint/test/build) он может коммитить локально в свою ветку.
- **Push** возможен только с одобрением пользователя (нативный fallback `shell *` → `ask`); прямые формы force push и удаления веток на origin (`--force*`, короткий `-f` в ведущей/средней/крайней позиции, короткие кластеры, `+`-рефспеки, `--delete`, короткий `-d`, `:`-рефспеки, `--mirror`, `--prune`, плюс прямые формы `git -C <путь> push ...`) запрещены нативно (deny) для явно заматченных форм.
- Средства permissions — glob-матчинг по тексту разобранных сегментов команды; это **не песочница** для произвольных кодовых обёрток (`pnpm exec ...`, make-рецепты, git-хуки, тест-харнессы): если сегмент не попал под точное правило — требует одобрения OpenCode.
- Shell-allowы имплементора — точные команды проекта (go build/vet/test ./..., golangci-lint, проверочные цели make, скрипты pnpm, `git add`/`git commit`); `pnpm exec`, `go run`, dev-серверы, фокус-тесты и произвольные make-цели под allow не подпадают и запрашивают одобрение.
- **Имплементор и оркестратор НЕ имеют права:** мержить в `main`, force push, удалять ветки, коммитить чужие файлы. Нативно deny зашит для прямых форм force push и удаления веток на origin, force-удаления веток (`-D`, долгое `--delete --force`, короткие кластеры `-df`/`-fd`) и force-формы `git worktree remove`; мерж в `main` и обычное удаление локальной ветки (`git branch -d`) — запрет инструкцией, а не нативным permission (у оркестратора `git branch -d`/`--delete` — `ask`). Интеграция — решение человека.
- **Слияние — из основной папки или через PR на GitHub**, никогда из worktree тикета.
- **Чистка после мержа:** после подтверждения пользователем, что тикет замержен, и после одобрения пользователем (нативное permission `ask` на `git worktree remove` / `git branch -d`) оркестратор из основной папки удаляет чистый worktree и его **локальную** ветку тикета. Никогда не `--force`; ветку тикета на origin не удаляем. Если worktree грязный, ветка не замержена или оркестратор не уверен — он останавливается и спрашивает.
- Перед стартом нового тикета — `git pull` в основной папке, ветка от свежего `main`.
- Если в процессе нужна свежая `main` внутри своей ветки — `git merge main` в своей ветке, не наоборот.

## Review process

- После реализации тикета — ревью по скиллу `code-review`: **две независимые оси** (Standards + Spec), каждая — **отдельным свежим дочерним сеансом** субагента `reviewer` (профиль `.opencode/agents/reviewer.md`, read-only), запускаемыми параллельно со своими промптами. Отдельная основная/TUI-сессия для ревью не требуется.
- Ревьюер read-only (правки запрещены на уровне permissions): находки передаются оркестратору, код правит имплементор.
- Фиксированная точка по умолчанию — `main...HEAD` своей ветки (или `main...origin/ticket/...` для ревью чужой ветки), если пользователь не указал иное.
- Источники для Spec-оси — локальные: тикет в `docs/tickets/` и релевантная часть `docs/SPEC.md`; внешний issue-tracker не требуется.
- **Повторное ревью после фиксов** — только дельта: `git diff <sha-до-фиксов>...HEAD`, без полного прогона. Приоритет перепроверки — поведенческие баги; фикс поведенческого бага обязан идти с регрессионным тестом — тест и есть доказательство.
- Полный повторный прогон двух осей — только если фиксы переписали значительную часть дифа (грубо >30%) или первое ревью нашло архитектурную проблему.
- Запахи из ревью — judgement calls: автор вправе отклонить с объяснением; нарушения документированных стандартов — не вправе.

## Учебная программа

Три блока (~35–40 ч), порядок фиксированный — см. `PLAN.md`. Первый tracer-модуль: бинарный поиск (сквозная вертикаль алгоритм → кадры → SSE → TS-рендерер).
