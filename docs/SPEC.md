# Спека: обучающий проект «Визуализатор алгоритмов»

> Метка: `ready-for-agent`
> Источники: интервью (grill-with-docs), [GLOSSARY.md](../GLOSSARY.md), [docs/adr/](adr/), [PLAN.md](../PLAN.md)

## Problem Statement

Учащийся хочет системно прокачать алгоритмы по структурированной программе (~35–40 ч) и параллельно освоить работу с ИИ-агентами в парадигме SDD. Классические материалы (книги, лекции) дают теорию без «живого» понимания: невозможно увидеть, как алгоритм движется по массиву или дереву шаг за шагом. Существующий репозиторий — однофайловый демо-код без визуализации, тестов и учебной структуры.

## Solution

Приложение из трёх независимых слоёв:

1. **Библиотека алгоритмов** — чистый Go-код, переиспользуемый, не знающий о UI. Каждый алгоритм умеет работать в quiet mode (обычная функция) и опционально эмитировать события шагов (Emitter, ADR-0001).
2. **Визуализатор** — Go-сервер + TS-фронтенд. Бэкенд превращает события в кадры-снапшоты (Frame, ADR-0002) и стримит их по SSE (ADR-0003); фронтенд — тупой рендерер кадров с плеером (play/pause/скорость/перемотка).
3. **CLI-квиз** — интерактивный опросник по программе обучения: вопросы из embedded-хранилища по блокам, сводка результатов.

Учебная программа — три блока (Фундамент, Деревья, Графы+ДП). Учебный Module может быть разбит на несколько вертикальных тикетов и рабочих сессий; один worktree/ветка = один тикет. Строка модуля в `PROGRESS.md` отмечается только после всех его обязательных частей.

## User Stories

### Обучение и прогресс

1. As a учащийся, I want to пройти программу обучения блок за блоком в фиксированном порядке, so that каждый следующий модуль опирается на уже пройденный.
2. As a учащийся, I want to видеть чек-лист прогресса по всем модулям, so что понимать, где я нахожусь в программе.
3. As a учащийся, I want to проходить учебный модуль небольшими вертикальными тикетами, so что каждая рабочая сессия имеет обозримый результат, а модуль считается завершённым только после всех частей.
4. As a учащийся, I want to помечать модуль завершённым только когда готовы все части (алгоритм, тесты, визуализация, вопросы квиза), so что «пройдено» означает «пройдено целиком».

### Библиотека алгоритмов

5. As a Go-разработчик, I want to использовать алгоритмы как обычную библиотеку без импорта визуального слоя, so что код переиспользуется вне проекта.
6. As a учащийся, I want to читать комментарии на русском, объясняющие идею алгоритма, so что код самодокументирован для обучения.
7. As a учащийся, I want to наблюдать quiet mode каждого алгоритма — без событий, только результат, so что библиотечное поведение не замусорено визуальной обвязкой.

### Визуализатор

8. As a учащийся, I want to открыть в браузере список доступных визуализаций и выбрать алгоритм, so что начать наблюдение без настройки.
9. As a учащийся, I want to задать входные данные для запуска алгоритма, so что смотреть выполнение на своих примерах.
10. As a учащийся, I want to видеть анимацию выполнения алгоритма шаг за шагом, so что понимать его механику наглядно.
11. As a учащийся, I want to управлять плеером (пауза, воспроизведение, скорость, шаг вперёд/назад), so что разбирать непонятные места в своём темпе.
12. As a учащийся, I want to читать пояснение к каждому шагу на экране, so что понимать, что именно происходит в кадре.
13. As a учащийся, I want to видеть подсветку активных элементов (сравниваемые, обмениваемые, посещаемые), so что взгляд сразу цепляется за действие.
14. As a учащийся, I want к визуализациям разных типов структур (массив, дерево, граф) с рендером, подходящим каждой структуре, so что деревья выглядят как деревья, а графы как графы.
15. As a учащийся, I want to перематывать выполнение к любому шагу, so что возвращаться к началу без перезапуска.

### Квиз

16. As a учащийся, I want to пройти интерактивный квиз по выбранному блоку, so что проверить теорию после прохождения модулей.
17. As a учащийся, I want to получить пояснение после каждого ответа (почему правильно/неправильно), so что квиз тоже учит.
18. As a учащийся, I want to видеть сводку результатов в конце (правильные/всего по каждому блоку), so что понять, что нужно повторить.
19. As a учащийся, I want к вопросам, привязанным к конкретным модулям, so что квиз отражает то, что реально реализовано.

### Агент и процесс

20. As a агент, I want to иметь глоссарий и ADR, so что использовать канонический язык проекта и не переоткрывать принятые решения.
21. As a агент, I want к спеке и тикетам в репозитории, so что реализация идёт по зафиксированным требованиям, а не по памяти диалога.
22. As a учащийся, I want к коду, покрытому тестами на публичных швах алгоритмов, SSE, квиза и фронтенда, so что рефакторинг и новые модули не ломают существующее.

## Implementation Decisions

- **Три слоя, жёсткая граница**: `algorithms` (библиотека), `visual` (сервер + фронтенд), `quiz` (CLI). Библиотека не импортирует и не знает о визуализации и квизе.
- **Emitter + типизированные события (ADR-0001)**: каждый визуализируемый алгоритм принимает опциональный Emitter и стреляет своими типами событий (сравнение, обмен, визит вершины...). Протокол записи общий, типы событий — свои у алгоритма.
- **Quiet mode**: без эмиттера алгоритм — обычная функция. Основной режим для тестов и переиспользования.
- **Кадры (ADR-0002)**: бэкендовый Frame Renderer превращает события алгоритма в кадры: снимок структуры (массив/дерево/граф), подсветки, текст пояснения на русском. Свой Frame Renderer на каждый визуализируемый алгоритм.
- **Транспорт SSE (ADR-0003)**: сервер отдаёт поток кадров одним SSE-соединением; пауза/скорость/перемотка — локальное управление кадрами на клиенте; новый ввод = новый запрос.
- **Фронтенд**: Vite + ванильный TypeScript, без фреймворка; отрисовка кадров в DOM/SVG. Словарь UI на русском (i18n — позже, out of scope v1).
- **Go-модуль**: `github.com/EvgeniiIvanov/algo`; репозиторий `git@github.com:EvgeniiIvanov/algo.git`.
- **Квиз**: движок с подменяемым stdin/stdout; вопросы — embedded JSON/YAML по блокам; формат вопроса: текст, 4 варианта, ровно один правильный, пояснение, ссылка на модуль. Результат — сводка в конце, история попыток не хранится.
- **Языки**: UI и комментарии — русский; идентификаторы, имена пакетов — английский.
- **Прогресс**: чек-лист в PROGRESS.md по блокам, одна строка на модуль, ведётся руками.
- **Текущий однофайловый код удаляется в первом тикете** без переноса (ADR-0001-совместимые реализации будут написаны заново чище).
- **Порядок программы**: строго Блок 1 → 2 → 3; теоретические темы (Big O, P/NP, B-деревья) = модуль «только квиз» без визуализации.
- **Первый tracer-модуль**: бинарный поиск — сквозная вертикаль (алгоритм → события → кадры → SSE → TS-рендерер) на минимальном наборе событий.

## Testing Decisions

- Хороший тест проверяет внешнее поведение, не внутреннее устройство: что алгоритм сортирует/находит/вставляет, что SSE-поток содержит ожидаемую последовательность кадров, что квиз правильно считает сводку.
- **Три основных шва и отдельный фронтенд-шов (ниже публичных интерфейсов не опускаемся):**
  1. Публичный API пакетов алгоритмов (quiet mode): unit-тесты внешнего поведения — результат, инварианты (например, BST-инвариант после серии вставок), граничные случаи (пустой вход, один элемент, отсутствие элемента).
  2. SSE-эндпоинт визуализатора: интеграционный тест — вход → чтение SSE-потока → сравнение последовательности кадров с ожидаемой. Покрывает emitter, Frame Renderer и HTTP-слой одной проверкой.
  3. Движок квиза: тесты со скриптованным вводом (подменённый stdin/stdout) — подсчёт результата, сводка; плюс валидация Quiz Bank (ровно один правильный ответ, есть пояснение и ссылка на модуль).
- **Четвёртый шов (фронтенд визуализатора)**: по решению code-review при тикете 03 — отдельный шов `visual/frontend` (бэкенд не знает про фронт). Покрывает публичные модули `sse`, `player`, `stream`, `render`, парсеры `binarysearch`/`scenario` и общую грамматику `decimalInteger`: кадры SSE и ввод до Run, play/pause/seek/stepForward/Backward/setSpeed/subscribe/load/append, сетевые ошибки и AbortError, рендер `array` и видов `structure`. DOM ниже публичного `render`-интерфейса и `fetch` без инъекции не тестируем.
- На старте перезапущенного репозитория prior art отсутствовал; тикеты 01–04 (трейсер) установили шаблоны тестов для последующих модулей.

## Out of Scope

- Живое управление запуском по WebSocket (команды с клиента во время выполнения).

# Модуль: Линейные структуры — стек, очередь, список на слайсе и односвязный список (Блок 1)

> Метка: `ready-for-agent`
> Статус: утверждена (Ч1 пройден), разбита на тикеты 08–12 (Ч2 пройден). Проектные решения выше (слои, Emitter, Frame, SSE, квиз) остаются каноническими; здесь — только специфика модуля.

## Problem Statement

По программе Блока 1 после Big O, бинарного поиска и рекурсии идут базовые линейные структуры данных. Учащийся должен своими руками собрать стек и очередь, список на слайсе и односвязный список на Go, почувствовать разницу стоимости операций (переполнение фиксированных структур, O(n) dequeue со сдвигом, амортизированный O(1) при вставке в конец растущего списка, O(n) вставка в середину) и увидеть это в визуализаторе. Инфраструктура трейсера (Emitter, Frame, SSE, TS-плеер, движок квиза) готова — модуль добавляет контент поверх неё.

## Solution

1. **Библиотека**: пакет структур (`structures` по PLAN.md) — Stack, Queue, List на слайсах и LinkedList (односвязный, на указателях). Каждая структура работает в quiet mode и опционально эмитирует события операций (ADR-0001).
2. **Визуализатор**: новый вид кадра «линейная структура» — снимок содержимого с подсветкой затронутых элементов и указателями (top у стека, head/tail у очереди; списку на слайсе указатели не нужны — его ряд рисуется только из существующих значений, а head для односвязного списка решается тикетом 11). Связный список рендерится узлами со стрелками next — видно, что это не непрерывная память, и как обход идёт узел за узлом. Вход — не массив, а сценарий операций, который выполняется шаг за шагом.
3. **Квиз**: новый модуль в `block-1` банка вопросов (5–8 вопросов): сложность операций, LIFO/FIFO, рост слайса и амортизация, массив vs связный список — теперь на собственной реализации обеих сторон сравнения.

## User Stories

1. As a учащийся, I want to реализовать стек фиксированной ёмкости на слайсе (push/pop/peek/len), so that понять LIFO и цену ограниченной ёмкости — переполнение как явную ошибку.
2. As a учащийся, I want to реализовать очередь на слайсе (enqueue/dequeue/len), so that понять FIFO и почему наивный dequeue со сдвигом — это O(n).
3. As a учащийся, I want to реализовать список на слайсе со вставкой и удалением по индексу, so that увидеть сдвиг элементов и линейную стоимость операций в середине.
4. As a учащийся, I want to реализовать односвязный список на указателях (вставка в голову/хвост/по индексу, удаление, поиск), so that почувствовать на своём коде, где он выигрывает у массива (вставка в голову O(1)) и где проигрывает (доступ по индексу — обход O(n)).
5. As a учащийся, I want к событиям каждой операции (что записали/удалили/сдвинули и по каким индексам; какой узел посетили при обходе; какую связь переключили), so that визуализатор мог показать шаг без знания внутренностей структуры.
6. As a учащийся, I want to ввести сценарий операций (например, `push 5`, `push 7`, `pop`) и прогнать его в визуализаторе, so that наблюдать поведение структуры на своих примерах.
7. As a учащийся, I want to видеть в кадре содержимое структуры, подсветку затронутых элементов и указатели (top, head/tail), so that взгляд сразу цеплялся за действие операции; для связного списка — узлы со стрелками next и подсветку текущего узла обхода, so that видеть цену доступа по индексу глазами.
8. As a учащийся, I want to читать пояснение к каждому шагу операции, so that понимать, что именно произошло в кадре.
9. As a учащийся, I want to проверить себя квизом по модулю, so that закрепить сложность операций, различие LIFO/FIFO и компромиссы «массив vs связный список».
10. As a Go-разработчик, I want to использовать структуры как обычный пакет без импорта визуального слоя, so что код переиспользуется вне проекта.
11. As a агент, I want к шаблону трейсера (события → Frame Renderer → SSE-маршрут → TS-рендер → тесты на швах), so что модуль повторяет установленные практики без новой архитектуры.

## Implementation Decisions

- **Пакет**: `algorithms/structures` — общий дом для структур Блока 1 (сюда же позже ляжет хеш-таблица). Один пакет, четыре типа: Stack, Queue, List (на слайсах) и LinkedList (односвязный, на указателях). Общие ошибки пакета (`ErrIndexOutOfRange`, `ErrListEmpty`, `ErrQueue*`, `ErrStack*`) живут централизованно в `errors.go`.
- **Элементы — int**: как в трейсере; обобщение (generics) — out of scope модуля.
- **Минимальные интерфейсы**: Stack — NewStack(size) (*Stack, error; конструктор переименован из New в NewStack по решению пользователя, тикет 09; отрицательная ёмкость — ошибка, не паника)/Push/Pop/Peek/Len (по черновику пользователя стек **фиксированной ёмкости**: Push возвращает ошибку переполнения; дополнительно Cap/IsEmpty/IsFull/Clear из черновика); Queue — по черновику пользователя (тикет 09) фиксированной ёмкости: NewQueue(max) (*Queue, error; отрицательная ёмкость — ошибка)/Enqueue/Dequeue/Peek/Len (+IsEmpty/IsFull/Clear); Enqueue в полную очередь — ошибка переполнения, Dequeue из пустой — ошибка; Dequeue **сдвигает** оставшиеся элементы влево — наивная O(n) цена dequeue осознанно сохранена из черновика как учебная цель модуля; List — Insert/RemoveAt/Get/Len (растущий — здесь живут темы амортизации и роста слайса; индексы Insert — 0..Len включительно, вставка в голову и хвост легальна, RemoveAt — 0..Len-1; индекс вне границ — ErrIndexOutOfRange); LinkedList — Prepend/Append/InsertAt/RemoveAt/Find/Len (по принятой доработке черновика тикета 11: **Find ищет значение, а не индекс** (`Find(value int) int`) — возвращает позицию первого узла с этим значением, при промахе -1 и это не ошибка, как у бинарного поиска трейсера; учебная цель — увидеть скрытый обход узел за узлом; поддерживаются tail/size — Append в хвост O(1); сверх минимума спеки в черновике добавлены PopFront/PopBack/IsEmpty — оставляем: снимание с головы/хвоста полезно для инварианта tail; плюсы/минусы: хвост удаляется за O(n), потому что в односвязном списке нет prev). Операции с ошибкой (создание с отрицательной ёмкостью, pop из пустого, push в полный, dequeue из пустой, индекс вне границ) возвращают ошибку — паник нет.
- **События**: свои типы у каждой структуры, протокол общий (Emitter, ADR-0001). Событие описывает атомарный шаг операции: запись по индексу, удаление, сдвиг диапазона; у связного списка — визит узла при обходе и переключение связи (с позициями затронутых узлов). Достаточно, чтобы Frame Renderer построил кадр, не зная внутренностей.
- **Quiet mode**: без эмиттера структуры — обычные типы без накладных расходов; события опциональны.
- **Учебный контракт**: черновик структур пишет пользователь (`автор-черновик: человек` в тикетах библиотеки); агент дорабатывает по находкам ревью, черновик молча не переписывает.
- **Кадр**: новый Kind «structure» (по правилу render.ts: новый kind — новая ветка без правок существующих). Снимок: идентичность структуры (stack/queue/list/linked-list), содержимое (значения в порядке следования), подсветки (затронутые позиции с ролью — добавлен/удалён/сдвинут/посещён; у связного списка ещё «перелинкован» role `relinked` и «найдено» role `found`), указатели (top, head, tail — по структуре; для связного списка head — узел 0, tail — последний), имя операции. Один Kind на все четыре структуры. Для фиксированных Stack и Queue кадр несёт заданную ёмкость и весь ряд ячеек, включая пустые — переполнение читается глазами.
- **Рендер по идентичности структуры**: слайсовые структуры — непрерывные ячейки (как массив в трейсере); связный список — узлы со стрелками next и разрывами между ними, указатель head, подсветка узла обхода. Одна ветка Kind'а, переключение по полю снимка.
- **Ёмкость в кадрах**: у фиксированных Stack и Queue она показывается целиком, включая пустые ячейки; ёмкость растущего List-слайса не показываем — поле Capacity снимка списка равно текущей длине, ряд рисуется только из существующих значений (0 — пустой список). Рост и амортизация объясняются текстом пояснений и вопросами квиза.
- **Предел длины списка в Run**: визуализация списка ограничена `maxListLength` = 100 (`visual/server/list.go`), зеркальная pre-run валидация на фронте (`visual/frontend/src/scenario.ts`, `MAX_LIST_LENGTH`). Это safety bound одного визуального Run ради обозримого ряда ячеек и потока кадров — не предел библиотечного `algorithms/structures.List`: библиотечная структура растёт без ограничения, темы амортизации и роста слайса остаются в квизе. Фиксированные Stack и Queue — вдоль ёмкостного предела (capacity 1..100) на тех же основаниях. Для односвязного списка — те же цифры на тех же основаниях: `maxLinkedLength`/`maxLinkedOps` в `visual/server/linkedlist.go` и `MAX_LINKED_LENGTH`/`MAX_LINKED_OPS` на фронте; каждое событие (и каждый визит обхода) — отдельный кадр, поэтому предел сценария важен ещё и для размера потока. Библиотечный `LinkedList` лимитов не имеет.
- **Вход визуализатора**: сценарий операций текстом, одна операция на строку (`push 5`, `pop`, `enqueue 3`, `insert 1 9`, `remove 0`, `prepend 4`, `append 7`, `find 7`); ошибки парсинга — понятным сообщением до старта Run. Выбор структуры — в UI рядом с полем сценария; для фиксированных Stack и Queue задаётся ёмкость. Поиск `find` отсутствующего значения — не ошибка входа, а успешный промах: кадры показывают обход и возврат -1.
- **Сервер**: по тонкому маршруту на структуру (`/api/run/stack`, `/api/run/queue`, `/api/run/list`, `/api/run/linked-list`) — повторяет шаблон трейсера: парсинг → валидация → runStreaming, транспорт не правится.
- **Квиз**: модуль `structures` в `block-1` банка, 5–8 вопросов в существующем формате; порядок в блоке — после `recursion`. Темы: LIFO/FIFO, сложность операций, амортизация и рост слайса, массив vs связный список (обход, вставка в голову, память) на собственной реализации.
- **PROGRESS.md**: строка модуля отмечается по завершении всех его частей.

## Testing Decisions

- Новых швов нет — модуль ложится на существующие четыре; prior art — тикеты 01–04 (трейсер).
- **Шов 1 (публичный API структур, quiet mode)**: поведение операций, инварианты LIFO/FIFO, граничные случаи (пустые и полные Stack/Queue, отрицательная ёмкость, индекс вне границ, чередование операций); у связного списка — инвариант связности (обход от головы даёт ровно Len узлов), удаление головы/хвоста, поиск отсутствующего; эмиттер-шпион фиксирует последовательность событий на известном сценарии, включая сдвиги очереди и визиты узлов при обходе.
- **Шов 2 (SSE-эндпоинт)**: сценарий операций → чтение SSE-потока → сравнение последовательности кадров с ожидаемой (хотя бы один маршрут полностью, остальные — на ключевых сценариях).
- **Шов 3 (квиз)**: существующая валидация банка покрывает новый модуль автоматически.
- **Шов 4 (фронт)**: рендер кадра нового Kind'а (обе разновидности: ячейки и узлы со стрелками), парсинг сценария операций, ошибки ввода. DOM ниже публичного API не трогаем.

## Out of Scope

- Двусвязный и циклический списки; расширенный API связного списка (Reverse, Sort и т.п.).
- Generics, конкурентный доступ, сериализация структур.
- Визуализация внутренней capacity и перевыделения backing array растущего List-слайса; адресов памяти узлов. Заданная ёмкость фиксированных Stack/Queue при этом отображается.
- Редактор сценариев с подсветкой синтаксиса, сохранение сценариев.
- Изменения транспорта SSE и плеера — инфраструктура трейсера не трогается.

# Модуль: «Хеш-таблицы с коллизиями» (Блок 1)

> Метка: `ready-for-agent`
> Статус: утверждена (Ч1 пройден), разбита на тикеты 15–16 (Ч2 пройден).

## Problem Statement

После линейных структур учащийся должен понять, как хранить пары «ключ — значение» и получать значение по ключу, не перебирая всю коллекцию. Важная часть темы — коллизии: разные ключи могут попасть в один bucket, и реализация должна разрешить столкновение и сохранить доступность обеих записей. Готовый `map` Go скрывает эти механизмы, поэтому нужна собственная небольшая реализация с наблюдаемыми шагами.

## Solution

Добавить учебную хеш-таблицу в общий пакет структур. Используется таблица фиксированного числа buckets с разрешением коллизий методом цепочек: bucket хранит несколько пар ключ-значение. Реализация работает в quiet mode и может выдавать типизированные события. Визуализатор принимает сценарий операций и рисует buckets с цепочками, а квиз закрепляет хеширование, коллизии и сложность операций.

## User Stories

1. As a учащийся, I want to хранить пары целочисленных ключей и значений в собственной таблице, so that понять базовую абстракцию «ключ — значение» без скрывающего детали `map`.
2. As a учащийся, I want to выбирать положительное число buckets, so that наблюдать, как ёмкость bucket-массива влияет на распределение ключей.
3. As a учащийся, I want to добавлять пару по ключу и обновлять значение уже существующего ключа, so that один ключ соответствовал ровно одной актуальной записи.
4. As a учащийся, I want to искать ключ и различать найденное значение и промах, so that понимать поведение lookup.
5. As a учащийся, I want to удалять ключ, сохраняя остальные записи той же цепочки, so that увидеть, как удаление работает при коллизиях.
6. As a учащийся, I want to наблюдать вычисление bucket-индекса и обход цепочки, so that видеть цену поиска при удачном распределении и при коллизиях.
7. As a учащийся, I want to прогонять текстовый сценарий `put`, `get`, `delete`, so that разбирать собственные примеры без изменения кода.
8. As a учащийся, I want to видеть все buckets и цепочки ключ-значение в каждом кадре, so that сравнивать пустые buckets, одиночные записи и несколько столкнувшихся ключей.
9. As a учащийся, I want to читать пояснение к каждому шагу, включая обновление, найденный ключ и промах, so that связывать картинку с операцией.
10. As a учащийся, I want to пользоваться таблицей как обычной Go-структурой без визуального слоя, so that проверять её поведение в quiet mode и переиспользовать библиотечный API.
11. As a учащийся, I want к типизированным событиям операций, so that Frame Renderer строил кадры, не зная внутреннего устройства алгоритма.
12. As a учащийся, I want проверить себя квизом по коллизиям, цепочкам, buckets и ожидаемой/худшей сложности, so that закрепить компромиссы структуры.

## Implementation Decisions

- **Пакет и границы**: `algorithms/structures`, как для линейных структур. Алгоритм не импортирует `visual/` и `quiz/`; сохраняются ADR-0001–0003 и существующий транспорт SSE.
- **Учебный контракт**: человек пишет черновик HashTable до реализации библиотечного тикета (`автор-черновик: человек`). Агент дорабатывает его по итогам ревью, не переписывая молча.
- **Тип данных**: целочисленный ключ и целочисленное значение; generics и произвольные типы ключей не входят в начальную реализацию.
- **Модель**: фиксированное положительное число buckets; коллизии разрешаются отдельными цепочками. Функция для целочисленного ключа — остаток от деления на число buckets с нормализацией отрицательного остатка в диапазон индексов. Например, при пяти buckets ключи `1` и `6` попадают в один bucket. Модель выбрана, чтобы механизм коллизий был детерминированным и видимым.
- **Минимум API**: создание таблицы, `Put(key, value)`, `Get(key)` с результатом и признаком наличия, `Delete(key)` с признаком удаления и `Len()`. Повторный `Put` существующего ключа обновляет значение и не увеличивает длину. Неуспешный `Get`/`Delete` — обычный промах, не ошибка. Отрицательное или нулевое число buckets при создании возвращает ошибку, не панику.
- **Изоляция темы**: таблица не растёт и не выполняет rehash; число buckets задаётся при создании. Это оставляет фокус на bucket-индексе, коллизиях и обходе цепочек. Вставка, поиск и удаление затрагивают только выбранный bucket.
- **События**: собственные типизированные события описывают выбранный bucket, посещение записи цепочки, вставку/обновление/удаление и результат поиска (найдено/не найдено). Событий достаточно, чтобы восстановить смысл каждого шага; алгоритм не создаёт текстовые UI-логи.
- **Визуальный контракт**: сценарий — по одной операции на строку: `put <key> <value>`, `get <key>`, `delete <key>`. Пользователь задаёт число buckets. Ошибки синтаксиса, целых чисел и конфигурации сообщаются до Run; промахи `get` и `delete` показываются как успешные шаги сценария.
- **Кадры**: каждый кадр — полный самодостаточный снимок (ADR-0002), содержащий число buckets, записи каждой цепочки, подсветки выбранного bucket/посещённой/изменённой записи, надгробия удалённых на этом шаге записей (ключ, значение и бывшая позиция в цепочке — сам снимок корзин их уже не содержит), имя операции и пояснение на русском. Для отдельной формы bucket-массива используется новый `kind` кадра `hash-table`, чтобы не менять контракт `kind="structure"` линейных структур.
- **Сервер и фронтенд**: тонкий маршрут `/api/run/hash-table` повторяет существующий шаблон парсинг → валидация → `runStreaming`; общий SSE-транспорт не меняется. Фронтенд добавляет ввод сценария и рендер buckets с цепочками; существующие рендеры остаются рабочими.
- **Ограничения Run**: для визуализации — 1–100 buckets, не более 100 одновременно хранимых записей и не более 500 операций; frontend и сервер зеркально проверяют их до Run. Это лимиты одного визуального запуска, не библиотечной таблицы. На операцию приходится не более события выбора bucket, события на каждую посещённую запись и одного события результата/изменения; с максимум 100 записями и 500 операциями верхняя граница потока — 51 001 кадр (включая начальный). Удаление не добавляет кадр сверх события изменения: удалённая запись живёт в снимке этого же кадра надгробием на бывшей позиции. Событие выбора bucket несёт сырой остаток ключа — объяснение расчёта рендер собирает из события, не повторяя формулу библиотеки. Отдельного отсечения уже начатого SSE-потока нет.
- **Квиз**: модуль `hash-tables` в `block-1`, 5–8 вопросов в существующем формате. Темы: ключ/bucket/hash-индекс, коллизия, разрешение цепочками, обновление и удаление, средняя и худшая сложность, влияние распределения и заполненности buckets.
- **PROGRESS.md**: строка «Хеш-таблицы с коллизиями» отмечается только после завершения обязательных частей модуля.

## Testing Decisions

- Хороший тест проверяет внешнее поведение и публичные контракты, а не конкретную внутреннюю форму узлов/слайсов.
- **Шов 1 — публичный API**: поведение `Put`/`Get`/`Delete`/`Len`, пустая таблица, обновление существующего ключа, промахи, отрицательные ключи, ошибки размера и несколько ключей с одинаковым bucket-индексом; emitter-шпион проверяет значимую последовательность событий на сценарии с коллизией.
- **Шов 2 — SSE-эндпоинт**: известный сценарий с коллизией → чтение `/api/run/hash-table` → сравнение последовательности самодостаточных кадров, включая выбор bucket и обход цепочки.
- **Шов 3 — квиз**: существующая валидация Quiz Bank проверяет 5–8 вопросов и формат; движок не меняется, если его публичный контракт не затрагивается.
- **Шов 4 — фронтенд**: публичные функции проверяют разбор корректных и некорректных сценариев и рендер пустых buckets, цепочки с коллизиями, попадания и промаха. DOM ниже публичного рендерера не тестируем.
- **Prior art**: публичные тесты Stack/Queue/List/LinkedList, SSE-тесты маршрутов структур и frontend-тесты парсера сценария/рендерера; нового тестового шва не вводим.

## Out of Scope

- Открытая адресация, линейное/квадратичное пробирование и другие стратегии разрешения коллизий.
- Динамический рост таблицы, rehash и автоматическая настройка числа buckets.
- Generics, произвольные типы ключей/значений, пользовательские hash-функции, криптографическая стойкость.
- Параллельный доступ, сериализация и постоянное хранение.
- Изменения общего Frame/SSE-транспорта, плеера или уже существующих визуализаций.

## Further Notes

- Целочисленные ключи/значения, modulo-хеширование и метод цепочек подтверждены на Ч1. Термины модуля определены в `GLOSSARY.md`.
- Worktree и статус `in-progress` относятся к конкретному тикету и создаются только после Ч2.

# Модуль: «Простые сортировки» (Блок 1)

> Метка: `ready-for-agent`
> Статус: утверждена (Ч1 пройден), разбита на тикеты 19–22 (Ч2 пройден).

## Problem Statement

После хеш-таблиц учащийся должен увидеть, как сравнения и перестановки постепенно упорядочивают массив, и сравнить несколько базовых алгоритмов по числу шагов, сложности и устойчивости. Пока в проекте нет сортировки, которую можно запустить как обычный алгоритм, наблюдать в визуализаторе и закрепить квизом.

## Solution

Добавить три простых алгоритма сравнения — bubble sort, selection sort и insertion sort — для целочисленного слайса. Каждый алгоритм работает в quiet mode и может сообщать типизированные события. Визуализатор принимает массив и выбранный алгоритм, показывает сравнения и изменения массива кадр за кадром; квиз закрепляет механику и характеристики трёх алгоритмов.

## User Stories

1. As a учащийся, I want to отсортировать массив целых чисел каждым из трёх простых алгоритмов, so that сравнить их на одинаковом входе.
2. As a учащийся, I want to запускать сортировки как обычные библиотечные функции без визуализатора, so that проверять результат и переиспользовать алгоритмы.
3. As a учащийся, I want to видеть каждое сравнение элементов, so that понимать, как алгоритм выбирает следующий шаг.
4. As a учащийся, I want to видеть каждую перестановку или запись значения в массив, so that связывать движение элементов с ходом алгоритма.
5. As a учащийся, I want к полному снимку массива на каждом кадре, so that использовать паузу и перемотку, не восстанавливая состояние из событий.
6. As a учащийся, I want to задавать массив с отрицательными числами и дубликатами, so that проверять сортировки на разнообразных данных.
7. As a учащийся, I want to наблюдать пустой, одноэлементный, уже отсортированный и обратный массивы, so that понимать граничные случаи и влияние начального порядка.
8. As a учащийся, I want к пояснению на русском для каждого кадра, so that понимать сравнение, обмен или сдвиг без чтения исходного кода.
9. As a учащийся, I want пройти квиз по механике, сложности и устойчивости сортировок, so that закрепить различия между алгоритмами.

## Implementation Decisions

- **Объём модуля**: bubble sort, selection sort и insertion sort. Merge sort и quicksort — следующий отдельный модуль по программе, не входят в этот тикетный набор.
- **Данные и порядок**: вход — `[]int`; результат упорядочен по возрастанию. Предлагаемый контракт библиотеки — сортировать переданный слайс на месте; пустой и одноэлементный слайсы допустимы. Дубликаты и отрицательные числа поддерживаются.
- **Варианты алгоритмов**: bubble sort завершает проходы досрочно, если обменов не было; selection sort выбирает минимум оставшейся части и меняет его с её первым элементом; insertion sort сдвигает только элементы, строго большие ключа. Это сохраняет устойчивость bubble/insertion и неустойчивость стандартного варианта selection.
- **Библиотека**: функции живут в `algorithms/sort`, не зависят от `visual/` и `quiz/`, работают в quiet mode и опционально принимают общий Emitter с типизированными событиями сравнения и изменения массива (ADR-0001). Каждый библиотечный тикет указывает `автор-черновик: человек`; до его реализации пользователь пишет и подтверждает черновик алгоритма на Ч2.5.
- **Визуализация**: отдельный выбор алгоритма и поле массива; сервер зеркально проверяет вход и ограничивает один визуальный Run ста элементами. Ошибка ввода возвращается до начала SSE. Кадры содержат полный снимок значений, выполняемую операцию, подсветку сравниваемых/изменяемых индексов и пояснение на русском. Один исходный кадр и дальнейшие кадры на события алгоритма; общий SSE-транспорт и плеер не меняются.
- **Контракт кадров**: сортировкам предлагается отдельный `kind="sort"`, а не изменение текущего `kind="array"` бинарного поиска. Так сохраняется существующий контракт массива и существующие визуализации; фронтенд добавляет отдельную ветку рендеринга.
- **Квиз**: новый модуль `simple-sorts` в `block-1`, после `hash-tables`, с 5–8 вопросами. Вопросы покрывают механику трёх алгоритмов, лучшую/среднюю/худшую сложность, устойчивость и граничные случаи; объяснения соответствуют выбранным выше вариантам.
- **PROGRESS.md**: строка «Сортировки простые» отмечается только после завершения библиотечной реализации, тестов, визуализации и квиза.

## Testing Decisions

- Хороший тест проверяет внешнее поведение: отсортированный результат, значимые события, SSE-кадры и публичное поведение фронтенд-парсера/рендерера; тесты не фиксируют внутреннюю реализацию циклов.
- **Шов 1 — публичный API алгоритмов**: каждый алгоритм проверяется на пустом и одноэлементном входах, уже/обратно отсортированных данных, дубликатах и отрицательных значениях; тесты с эмиттером проверяют значимую последовательность сравнений и изменений массива.
- **Шов 2 — SSE-эндпоинт**: интеграционный тест проходит от запроса Run до последовательности полных кадров. Покрываются все три алгоритма и валидируются отказ от некорректного входа и лимит длины до начала SSE.
- **Шов 3 — фронтенд визуализатора**: публичные функции проверяют разбор входного массива, построение URL и оба результата рендера (поддерживаемый кадр сортировки и некорректный снимок); DOM ниже публичного renderer-интерфейса и `fetch` без инъекции не тестируются.
- **Шов 4 — Quiz Bank**: существующая валидация проверяет новый модуль и формат 5–8 вопросов; движок квиза не меняется.
- Приоритет — существующие швы публичного API алгоритмов, SSE, фронтенд-рендера и Quiz Bank; новый общий тестовый шов не вводится.

## Out of Scope

- Merge sort, quicksort и другие алгоритмы сортировки — отдельный следующий модуль.
- Сортировка пользовательских типов, компараторы, generics и сортировка по убыванию.
- Замеры времени, графики производительности и автоматический подсчёт сравнений/обменов как отдельная аналитика.
- Изменения общего Frame/SSE-транспорта или плеера.

## Further Notes

- На Ч1 утверждены три алгоритма, их варианты, сортировка на месте и отдельный `kind="sort"`.
- Worktree и статус `in-progress` появляются только после утверждения тикетов на Ч2.
