# Спека: обучающий проект «Визуализатор алгоритмов»

> Метка: `ready-for-agent`
> Источники: интервью (grill-with-docs), [GLOSSARY.md](../GLOSSARY.md), [docs/adr/](adr/), [PLAN.md](../PLAN.md)

## Problem Statement

Учащийся хочет системно прокачать алгоритмы по структурированной программе (~35–40 ч) и параллельно освоить работу с ИИ-агентами в парадигме SDD. Классические материалы (книги, лекции) дают теорию без «живого» понимания: невозможно увидеть, как алгоритм движется по массиву или дереву шаг за шагом. Существующий репозиторий — однофайловый демо-код без визуализации, тестов и учебной структуры.

## Solution

Приложение из трёх независимых слоёв:

1. **Библиотека алгоритмов** — чистый Go-код, переиспользуемый, не знающий о UI. Каждый алгоритм умеет работать в quiet mode (обычная функция) и опционально эмитировать события шагов (Emitter, ADR-0001).
2. **Визуализатор** — Go-сервер + TS-фронтенд. Бэкенд превращает события в кадры-снапшоты (Frame, ADR-0002) и стримит их по SSE (ADR-0003); фронтенд — тупой рендерер кадров с плеером (play/pause/скорость/перемотка).
3. **CLI-квиз** — интерактивный опросник по программе обучения: вопросы из embedded-хранилища по блокам, сводка результатов.

Учебная программа — три блока (Фундамент, Деревья, Графы+ДП). Процесс: сессия с агентом = один Module (алгоритм + тесты + визуализация + вопросы квиза + запись в чек-листе прогресса).

## User Stories

### Обучение и прогресс

1. As a учащийся, I want to пройти программу обучения блок за блоком в фиксированном порядке, so that каждый следующий модуль опирается на уже пройденный.
2. As a учащийся, I want to видеть чек-лист прогресса по всем модулям, so что понимать, где я нахожусь в программе.
3. As a учащийся, I want to завершить один учебный модуль за одну сессию с агентом, so что каждая сессия проходит полный цикл SDD на обозримом объёме.
4. As a учащийся, I want to помечать модуль завершённым только когда готовы все части (алгоритм, тесты, визуализация, вопросы квиза), so что «пройдено» означает «пройдено целиком».

### Библиотека алгоритмов

5. As a Go-разработчик, I want to использовать алгоритмы как обычную библиотеку без импорта визуального слоя, so что код переиспользуется вне проекта.
6. As a учащийся, I want to читать комментарии на русском, объясняющие идею алгоритма, so что код самодокументирован для обучения.
7. As a учащийся, I want to наблюдать quiet mode каждого алгоритма — без событий, только результат, so что библиотечное поведение не замусорено визуальной обвязкой.

### Визуализатор

8. As a учащийся, I want to открыть в браузере список доступных визуализаций и выбрать алгоритм, so что начать наблюдение без настройки.
9. As a учащийся, I want to задать входные данные для запуска алгоритма, so что смотреть выполнение на своих примерах.
10. As a учащийся, I want to видеть анимацию выполнения алгоритма шаг за шагом, so что понимать его механику наглядно.
11. As a учащийся, I want to управлять плеером (пауза, воспроизведение, скорость, шаг вперёд/назад), so что разбирать непонятные места в своём темпе.
12. As a учащийся, I want to читать пояснение к каждому шагу на экране, so что понимать, что именно происходит в кадре.
13. As a учащийся, I want to видеть подсветку активных элементов (сравниваемые, обмениваемые, посещаемые), so что взгляд сразу цепляется за действие.
14. As a учащийся, I want к визуализациям разных типов структур (массив, дерево, граф) с рендером, подходящим каждой структуре, so что деревья выглядят как деревья, а графы как графы.
15. As a учащийся, I want to перематывать выполнение к любому шагу, so что возвращаться к началу без перезапуска.

### Квиз

16. As a учащийся, I want to пройти интерактивный квиз по выбранному блоку, so что проверить теорию после прохождения модулей.
17. As a учащийся, I want to получить пояснение после каждого ответа (почему правильно/неправильно), so что квиз тоже учит.
18. As a учащийся, I want to видеть сводку результатов в конце (правильные/всего по каждому блоку), so что понять, что нужно повторить.
19. As a учащийся, I want к вопросам, привязанным к конкретным модулям, so что квиз отражает то, что реально реализовано.

### Агент и процесс

20. As a агент, I want to иметь глоссарий и ADR, so что использовать канонический язык проекта и не переоткрывать принятые решения.
21. As a агент, I want к спеке и тикетам в репозитории, so что реализация идёт по зафиксированным требованиям, а не по памяти диалога.
22. As a учащийся, I want к коду, покрытому тестами на трёх швах, so что рефакторинг и новые модули не ломают существующее.

## Implementation Decisions

- **Три слоя, жёсткая граница**: `algorithms` (библиотека), `visual` (сервер + фронтенд), `quiz` (CLI). Библиотека не импортирует и не знает о визуализации и квизе.
- **Emitter + типизированные события (ADR-0001)**: каждый визуализируемый алгоритм принимает опциональный Emitter и стреляет своими типами событий (сравнение, обмен, визит вершины...). Протокол записи общий, типы событий — свои у алгоритма.
- **Quiet mode**: без эмиттера алгоритм — обычная функция. Основной режим для тестов и переиспользования.
- **Кадры (ADR-0002)**: бэкендовый Frame Renderer превращает события алгоритма в кадры: снимок структуры (массив/дерево/граф), подсветки, текст пояснения на русском. Свой Frame Renderer на каждый визуализируемый алгоритм.
- **Транспорт SSE (ADR-0003)**: сервер отдаёт поток кадров одним SSE-соединением; пауза/скорость/перемотка — локальное управление кадрами на клиенте; новый ввод = новый запрос.
- **Фронтенд**: Vite + ванильный TypeScript, без фреймворка; отрисовка кадров в DOM/SVG. Словарь UI на русском (i18n — позже, out of scope v1).
- **Go-модуль**: `github.com/EvgeniiIvanov/algo`; репозиторий `git@github.com:EvgeniiIvanov/algo.git`.
- **Квиз**: движок с подменяемым stdin/stdout; вопросы — embedded JSON/YAML по блокам; формат вопроса: текст, 4 варианта, ровно один правильный, пояснение, ссылка на модуль. Результат — сводка в конце, история попыток не хранится.
- **Языки**: UI и комментарии — русский; идентификаторы, имена пакетов — английский.
- **Прогресс**: чек-лист в PROGRESS.md по блокам, одна строка на модуль, ведётся руками.
- **Текущий однофайловый код удаляется в первом тикете** без переноса (ADR-0001-совместимые реализации будут написаны заново чище).
- **Порядок программы**: строго Блок 1 → 2 → 3; теоретические темы (Big O, P/NP, B-деревья) = модуль «только квиз» без визуализации.
- **Первый tracer-модуль**: бинарный поиск — сквозная вертикаль (алгоритм → события → кадры → SSE → TS-рендерер) на минимальном наборе событий.

## Testing Decisions

- Хороший тест проверяет внешнее поведение, не внутреннее устройство: что алгоритм сортирует/находит/вставляет, что SSE-поток содержит ожидаемую последовательность кадров, что квиз правильно считает сводку.
- **Три шва (по одному на слой, ниже не опускаемся):**
  1. Публичный API пакетов алгоритмов (quiet mode): unit-тесты внешнего поведения — результат, инварианты (например, BST-инвариант после серии вставок), граничные случаи (пустой вход, один элемент, отсутствие элемента).
  2. SSE-эндпоинт визуализатора: интеграционный тест — вход → чтение SSE-потока → сравнение последовательности кадров с ожидаемой. Покрывает emitter, Frame Renderer и HTTP-слой одной проверкой.
  3. Движок квиза: тесты со скриптованным вводом (подменённый stdin/stdout) — подсчёт результата, сводка; плюс валидация Quiz Bank (ровно один правильный ответ, есть пояснение и ссылка на модуль).
- Prior art в кодовой базе отсутствует (репозиторий перезапускается) — первый модуль-трейсер задаёт шаблон тестов для последующих.

## Out of Scope

- i18n UI (английский словарь) — позже.
- Живое управление запуском по WebSocket (команды с клиента во время выполнения).
- История попыток квиза / постоянное хранение результатов.
- Интерактивное редактирование сложных структур (конструктор деревьев/графов) — ввод через простые поля/JSON.
- B-деревья, KD-деревья, AVL/красно-чёрные деревья, TSP, алгоритм Литтла — концептуальные темы без реализации/визуализации.
- Хостинг/деплой — всё запускается локально.
- Настройка issue-трекера (GitHub issues) — спека и тикеты живут в репозитории.

## Further Notes

- Сессия с агентом = один Module; полный цикл SDD каждый раз (план модуля → реализация → тесты → вопросы квиза → обновление прогресса).
- Первый тикет-трейсер (бинарный поиск) устанавливает шаблоны: структура пакетов, формат событий, Frame Renderer, SSE-эндпоинт, TS-рендерер, тесты на всех трёх швах. Последующие модули повторяют шаблон.
- Метрика «достаточно хорошо» для визуализации: наглядно и управляемо, но не полирует сверх нужного — программа обучения важнее продукта.
