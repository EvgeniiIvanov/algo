# Спека: обучающий проект «Визуализатор алгоритмов»

> Метка: `ready-for-agent`
> Источники: интервью (grill-with-docs), [GLOSSARY.md](../GLOSSARY.md), [docs/adr/](adr/), [PLAN.md](../PLAN.md)

## Problem Statement

Учащийся хочет системно прокачать алгоритмы по структурированной программе (~35–40 ч) и параллельно освоить работу с ИИ-агентами в парадигме SDD. Классические материалы (книги, лекции) дают теорию без «живого» понимания: невозможно увидеть, как алгоритм движется по массиву или дереву шаг за шагом. Существующий репозиторий — однофайловый демо-код без визуализации, тестов и учебной структуры.

## Solution

Приложение из трёх независимых слоёв:

1. **Библиотека алгоритмов** — чистый Go-код, переиспользуемый, не знающий о UI. Каждый алгоритм умеет работать в quiet mode (обычная функция) и опционально эмитировать события шагов (Emitter, ADR-0001).
2. **Визуализатор** — Go-сервер + TS-фронтенд. Бэкенд превращает события в кадры-снапшоты (Frame, ADR-0002) и стримит их по SSE (ADR-0003); фронтенд — тупой рендерер кадров с плеером (play/pause/скорость/перемотка).
3. **CLI-квиз** — интерактивный опросник по программе обучения: вопросы из embedded-хранилища по блокам, сводка результатов.

Учебная программа — три блока (Фундамент, Деревья, Графы+ДП). Учебный Module может быть разбит на несколько вертикальных тикетов и рабочих сессий; один worktree/ветка = один тикет. Строка модуля в `PROGRESS.md` отмечается только после всех его обязательных частей.

## User Stories

### Обучение и прогресс

1. As a учащийся, I want to пройти программу обучения блок за блоком в фиксированном порядке, so that каждый следующий модуль опирается на уже пройденный.
2. As a учащийся, I want to видеть чек-лист прогресса по всем модулям, so что понимать, где я нахожусь в программе.
3. As a учащийся, I want to проходить учебный модуль небольшими вертикальными тикетами, so что каждая рабочая сессия имеет обозримый результат, а модуль считается завершённым только после всех частей.
4. As a учащийся, I want to помечать модуль завершённым только когда готовы все части (алгоритм, тесты, визуализация, вопросы квиза), so что «пройдено» означает «пройдено целиком».

### Библиотека алгоритмов

5. As a Go-разработчик, I want to использовать алгоритмы как обычную библиотеку без импорта визуального слоя, so что код переиспользуется вне проекта.
6. As a учащийся, I want to читать комментарии на русском, объясняющие идею алгоритма, so что код самодокументирован для обучения.
7. As a учащийся, I want to наблюдать quiet mode каждого алгоритма — без событий, только результат, so что библиотечное поведение не замусорено визуальной обвязкой.

### Визуализатор

8. As a учащийся, I want to открыть в браузере список доступных визуализаций и выбрать алгоритм, so что начать наблюдение без настройки.
9. As a учащийся, I want to задать входные данные для запуска алгоритма, so что смотреть выполнение на своих примерах.
10. As a учащийся, I want to видеть анимацию выполнения алгоритма шаг за шагом, so что понимать его механику наглядно.
11. As a учащийся, I want to управлять плеером (пауза, воспроизведение, скорость, шаг вперёд/назад), so что разбирать непонятные места в своём темпе.
12. As a учащийся, I want to читать пояснение к каждому шагу на экране, so что понимать, что именно происходит в кадре.
13. As a учащийся, I want to видеть подсветку активных элементов (сравниваемые, обмениваемые, посещаемые), so что взгляд сразу цепляется за действие.
14. As a учащийся, I want к визуализациям разных типов структур (массив, дерево, граф) с рендером, подходящим каждой структуре, so что деревья выглядят как деревья, а графы как графы.
15. As a учащийся, I want to перематывать выполнение к любому шагу, so что возвращаться к началу без перезапуска.

### Квиз

16. As a учащийся, I want to пройти интерактивный квиз по выбранному блоку, so что проверить теорию после прохождения модулей.
17. As a учащийся, I want to получить пояснение после каждого ответа (почему правильно/неправильно), so что квиз тоже учит.
18. As a учащийся, I want to видеть сводку результатов в конце (правильные/всего по каждому блоку), so что понять, что нужно повторить.
19. As a учащийся, I want к вопросам, привязанным к конкретным модулям, so что квиз отражает то, что реально реализовано.

### Агент и процесс

20. As a агент, I want to иметь глоссарий и ADR, so что использовать канонический язык проекта и не переоткрывать принятые решения.
21. As a агент, I want к спеке и тикетам в репозитории, so что реализация идёт по зафиксированным требованиям, а не по памяти диалога.
22. As a учащийся, I want к коду, покрытому тестами на публичных швах алгоритмов, SSE, квиза и фронтенда, so что рефакторинг и новые модули не ломают существующее.

## Implementation Decisions

- **Три слоя, жёсткая граница**: `algorithms` (библиотека), `visual` (сервер + фронтенд), `quiz` (CLI). Библиотека не импортирует и не знает о визуализации и квизе.
- **Emitter + типизированные события (ADR-0001)**: каждый визуализируемый алгоритм принимает опциональный Emitter и стреляет своими типами событий (сравнение, обмен, визит вершины...). Протокол записи общий, типы событий — свои у алгоритма.
- **Quiet mode**: без эмиттера алгоритм — обычная функция. Основной режим для тестов и переиспользования.
- **Кадры (ADR-0002)**: бэкендовый Frame Renderer превращает события алгоритма в кадры: снимок структуры (массив/дерево/граф), подсветки, текст пояснения на русском. Свой Frame Renderer на каждый визуализируемый алгоритм.
- **Транспорт SSE (ADR-0003)**: сервер отдаёт поток кадров одним SSE-соединением; пауза/скорость/перемотка — локальное управление кадрами на клиенте; новый ввод = новый запрос.
- **Фронтенд**: Vite + ванильный TypeScript, без фреймворка; отрисовка кадров в DOM/SVG. Словарь UI на русском (i18n — позже, out of scope v1).
- **Go-модуль**: `github.com/EvgeniiIvanov/algo`; репозиторий `git@github.com:EvgeniiIvanov/algo.git`.
- **Квиз**: движок с подменяемым stdin/stdout; вопросы — embedded JSON/YAML по блокам; формат вопроса: текст, 4 варианта, ровно один правильный, пояснение, ссылка на модуль. Результат — сводка в конце, история попыток не хранится.
- **Языки**: UI и комментарии — русский; идентификаторы, имена пакетов — английский.
- **Прогресс**: чек-лист в PROGRESS.md по блокам, одна строка на модуль, ведётся руками.
- **Текущий однофайловый код удаляется в первом тикете** без переноса (ADR-0001-совместимые реализации будут написаны заново чище).
- **Порядок программы**: строго Блок 1 → 2 → 3; теоретические темы (Big O, P/NP, B-деревья) = модуль «только квиз» без визуализации.
- **Первый tracer-модуль**: бинарный поиск — сквозная вертикаль (алгоритм → события → кадры → SSE → TS-рендерер) на минимальном наборе событий.

## Testing Decisions

- Хороший тест проверяет внешнее поведение, не внутреннее устройство: что алгоритм сортирует/находит/вставляет, что SSE-поток содержит ожидаемую последовательность кадров, что квиз правильно считает сводку.
- **Три основных шва и отдельный фронтенд-шов (ниже публичных интерфейсов не опускаемся):**
  1. Публичный API пакетов алгоритмов (quiet mode): unit-тесты внешнего поведения — результат, инварианты (например, BST-инвариант после серии вставок), граничные случаи (пустой вход, один элемент, отсутствие элемента).
  2. SSE-эндпоинт визуализатора: интеграционный тест — вход → чтение SSE-потока → сравнение последовательности кадров с ожидаемой. Покрывает emitter, Frame Renderer и HTTP-слой одной проверкой.
  3. Движок квиза: тесты со скриптованным вводом (подменённый stdin/stdout) — подсчёт результата, сводка; плюс валидация Quiz Bank (ровно один правильный ответ, есть пояснение и ссылка на модуль).
- **Четвёртый шов (фронтенд визуализатора)**: по решению code-review при тикете 03 — отдельный шов `visual/frontend` (бэкенд не знает про фронт). Покрывает публичные модули `sse`, `player`, `stream`, `render`, парсеры `binarysearch`/`scenario` и общую грамматику `decimalInteger`: кадры SSE и ввод до Run, play/pause/seek/stepForward/Backward/setSpeed/subscribe/load/append, сетевые ошибки и AbortError, рендер `array` и видов `structure`. DOM ниже публичного `render`-интерфейса и `fetch` без инъекции не тестируем.
- На старте перезапущенного репозитория prior art отсутствовал; тикеты 01–04 (трейсер) установили шаблоны тестов для последующих модулей.

## Out of Scope

- Живое управление запуском по WebSocket (команды с клиента во время выполнения).

# Модуль: Линейные структуры — стек, очередь, список на слайсе и односвязный список (Блок 1)

> Метка: `ready-for-agent`
> Статус: утверждена (Ч1 пройден), разбита на тикеты 08–12 (Ч2 пройден). Проектные решения выше (слои, Emitter, Frame, SSE, квиз) остаются каноническими; здесь — только специфика модуля.

## Problem Statement

По программе Блока 1 после Big O, бинарного поиска и рекурсии идут базовые линейные структуры данных. Учащийся должен своими руками собрать стек и очередь, список на слайсе и односвязный список на Go, почувствовать разницу стоимости операций (переполнение фиксированных структур, O(n) dequeue со сдвигом, амортизированный O(1) при вставке в конец растущего списка, O(n) вставка в середину) и увидеть это в визуализаторе. Инфраструктура трейсера (Emitter, Frame, SSE, TS-плеер, движок квиза) готова — модуль добавляет контент поверх неё.

## Solution

1. **Библиотека**: пакет структур (`structures` по PLAN.md) — Stack, Queue, List на слайсах и LinkedList (односвязный, на указателях). Каждая структура работает в quiet mode и опционально эмитирует события операций (ADR-0001).
2. **Визуализатор**: новый вид кадра «линейная структура» — снимок содержимого с подсветкой затронутых элементов и указателями (top у стека, head/tail у очереди; списку на слайсе указатели не нужны — его ряд рисуется только из существующих значений, а head для односвязного списка решается тикетом 11). Связный список рендерится узлами со стрелками next — видно, что это не непрерывная память, и как обход идёт узел за узлом. Вход — не массив, а сценарий операций, который выполняется шаг за шагом.
3. **Квиз**: новый модуль в `block-1` банка вопросов (5–8 вопросов): сложность операций, LIFO/FIFO, рост слайса и амортизация, массив vs связный список — теперь на собственной реализации обеих сторон сравнения.

## User Stories

1. As a учащийся, I want to реализовать стек фиксированной ёмкости на слайсе (push/pop/peek/len), so that понять LIFO и цену ограниченной ёмкости — переполнение как явную ошибку.
2. As a учащийся, I want to реализовать очередь на слайсе (enqueue/dequeue/len), so that понять FIFO и почему наивный dequeue со сдвигом — это O(n).
3. As a учащийся, I want to реализовать список на слайсе со вставкой и удалением по индексу, so that увидеть сдвиг элементов и линейную стоимость операций в середине.
4. As a учащийся, I want to реализовать односвязный список на указателях (вставка в голову/хвост/по индексу, удаление, поиск), so that почувствовать на своём коде, где он выигрывает у массива (вставка в голову O(1)) и где проигрывает (доступ по индексу — обход O(n)).
5. As a учащийся, I want к событиям каждой операции (что записали/удалили/сдвинули и по каким индексам; какой узел посетили при обходе; какую связь переключили), so that визуализатор мог показать шаг без знания внутренностей структуры.
6. As a учащийся, I want to ввести сценарий операций (например, `push 5`, `push 7`, `pop`) и прогнать его в визуализаторе, so that наблюдать поведение структуры на своих примерах.
7. As a учащийся, I want to видеть в кадре содержимое структуры, подсветку затронутых элементов и указатели (top, head/tail), so that взгляд сразу цеплялся за действие операции; для связного списка — узлы со стрелками next и подсветку текущего узла обхода, so that видеть цену доступа по индексу глазами.
8. As a учащийся, I want to читать пояснение к каждому шагу операции, so that понимать, что именно произошло в кадре.
9. As a учащийся, I want to проверить себя квизом по модулю, so that закрепить сложность операций, различие LIFO/FIFO и компромиссы «массив vs связный список».
10. As a Go-разработчик, I want to использовать структуры как обычный пакет без импорта визуального слоя, so что код переиспользуется вне проекта.
11. As a агент, I want к шаблону трейсера (события → Frame Renderer → SSE-маршрут → TS-рендер → тесты на швах), so что модуль повторяет установленные практики без новой архитектуры.

## Implementation Decisions

- **Пакет**: `algorithms/structures` — общий дом для структур Блока 1 (сюда же позже ляжет хеш-таблица). Один пакет, четыре типа: Stack, Queue, List (на слайсах) и LinkedList (односвязный, на указателях). Общие ошибки пакета (`ErrIndexOutOfRange`, `ErrListEmpty`, `ErrQueue*`, `ErrStack*`) живут централизованно в `errors.go`.
- **Элементы — int**: как в трейсере; обобщение (generics) — out of scope модуля.
- **Минимальные интерфейсы**: Stack — NewStack(size) (*Stack, error; конструктор переименован из New в NewStack по решению пользователя, тикет 09; отрицательная ёмкость — ошибка, не паника)/Push/Pop/Peek/Len (по черновику пользователя стек **фиксированной ёмкости**: Push возвращает ошибку переполнения; дополнительно Cap/IsEmpty/IsFull/Clear из черновика); Queue — по черновику пользователя (тикет 09) фиксированной ёмкости: NewQueue(max) (*Queue, error; отрицательная ёмкость — ошибка)/Enqueue/Dequeue/Peek/Len (+IsEmpty/IsFull/Clear); Enqueue в полную очередь — ошибка переполнения, Dequeue из пустой — ошибка; Dequeue **сдвигает** оставшиеся элементы влево — наивная O(n) цена dequeue осознанно сохранена из черновика как учебная цель модуля; List — Insert/RemoveAt/Get/Len (растущий — здесь живут темы амортизации и роста слайса; индексы Insert — 0..Len включительно, вставка в голову и хвост легальна, RemoveAt — 0..Len-1; индекс вне границ — ErrIndexOutOfRange); LinkedList — Prepend/Append/InsertAt/RemoveAt/Find/Len (по принятой доработке черновика тикета 11: **Find ищет значение, а не индекс** (`Find(value int) int`) — возвращает позицию первого узла с этим значением, при промахе -1 и это не ошибка, как у бинарного поиска трейсера; учебная цель — увидеть скрытый обход узел за узлом; поддерживаются tail/size — Append в хвост O(1); сверх минимума спеки в черновике добавлены PopFront/PopBack/IsEmpty — оставляем: снимание с головы/хвоста полезно для инварианта tail; плюсы/минусы: хвост удаляется за O(n), потому что в односвязном списке нет prev). Операции с ошибкой (создание с отрицательной ёмкостью, pop из пустого, push в полный, dequeue из пустой, индекс вне границ) возвращают ошибку — паник нет.
- **События**: свои типы у каждой структуры, протокол общий (Emitter, ADR-0001). Событие описывает атомарный шаг операции: запись по индексу, удаление, сдвиг диапазона; у связного списка — визит узла при обходе и переключение связи (с позициями затронутых узлов). Достаточно, чтобы Frame Renderer построил кадр, не зная внутренностей.
- **Quiet mode**: без эмиттера структуры — обычные типы без накладных расходов; события опциональны.
- **Учебный контракт**: черновик структур пишет пользователь (`автор-черновик: человек` в тикетах библиотеки); агент дорабатывает по находкам ревью, черновик молча не переписывает.
- **Кадр**: новый Kind «structure» (по правилу render.ts: новый kind — новая ветка без правок существующих). Снимок: идентичность структуры (stack/queue/list/linked-list), содержимое (значения в порядке следования), подсветки (затронутые позиции с ролью — добавлен/удалён/сдвинут/посещён; у связного списка ещё «перелинкован» role `relinked` и «найдено» role `found`), указатели (top, head, tail — по структуре; для связного списка head — узел 0, tail — последний), имя операции. Один Kind на все четыре структуры. Для фиксированных Stack и Queue кадр несёт заданную ёмкость и весь ряд ячеек, включая пустые — переполнение читается глазами.
- **Рендер по идентичности структуры**: слайсовые структуры — непрерывные ячейки (как массив в трейсере); связный список — узлы со стрелками next и разрывами между ними, указатель head, подсветка узла обхода. Одна ветка Kind'а, переключение по полю снимка.
- **Ёмкость в кадрах**: у фиксированных Stack и Queue она показывается целиком, включая пустые ячейки; ёмкость растущего List-слайса не показываем — поле Capacity снимка списка равно текущей длине, ряд рисуется только из существующих значений (0 — пустой список). Рост и амортизация объясняются текстом пояснений и вопросами квиза.
- **Предел длины списка в Run**: визуализация списка ограничена `maxListLength` = 100 (`visual/server/list.go`), зеркальная pre-run валидация на фронте (`visual/frontend/src/scenario.ts`, `MAX_LIST_LENGTH`). Это safety bound одного визуального Run ради обозримого ряда ячеек и потока кадров — не предел библиотечного `algorithms/structures.List`: библиотечная структура растёт без ограничения, темы амортизации и роста слайса остаются в квизе. Фиксированные Stack и Queue — вдоль ёмкостного предела (capacity 1..100) на тех же основаниях. Для односвязного списка — те же цифры на тех же основаниях: `maxLinkedLength`/`maxLinkedOps` в `visual/server/linkedlist.go` и `MAX_LINKED_LENGTH`/`MAX_LINKED_OPS` на фронте; каждое событие (и каждый визит обхода) — отдельный кадр, поэтому предел сценария важен ещё и для размера потока. Библиотечный `LinkedList` лимитов не имеет.
- **Вход визуализатора**: сценарий операций текстом, одна операция на строку (`push 5`, `pop`, `enqueue 3`, `insert 1 9`, `remove 0`, `prepend 4`, `append 7`, `find 7`); ошибки парсинга — понятным сообщением до старта Run. Выбор структуры — в UI рядом с полем сценария; для фиксированных Stack и Queue задаётся ёмкость. Поиск `find` отсутствующего значения — не ошибка входа, а успешный промах: кадры показывают обход и возврат -1.
- **Сервер**: по тонкому маршруту на структуру (`/api/run/stack`, `/api/run/queue`, `/api/run/list`, `/api/run/linked-list`) — повторяет шаблон трейсера: парсинг → валидация → runStreaming, транспорт не правится.
- **Квиз**: модуль `structures` в `block-1` банка, 5–8 вопросов в существующем формате; порядок в блоке — после `recursion`. Темы: LIFO/FIFO, сложность операций, амортизация и рост слайса, массив vs связный список (обход, вставка в голову, память) на собственной реализации.
- **PROGRESS.md**: строка модуля отмечается по завершении всех его частей.

## Testing Decisions

- Новых швов нет — модуль ложится на существующие четыре; prior art — тикеты 01–04 (трейсер).
- **Шов 1 (публичный API структур, quiet mode)**: поведение операций, инварианты LIFO/FIFO, граничные случаи (пустые и полные Stack/Queue, отрицательная ёмкость, индекс вне границ, чередование операций); у связного списка — инвариант связности (обход от головы даёт ровно Len узлов), удаление головы/хвоста, поиск отсутствующего; эмиттер-шпион фиксирует последовательность событий на известном сценарии, включая сдвиги очереди и визиты узлов при обходе.
- **Шов 2 (SSE-эндпоинт)**: сценарий операций → чтение SSE-потока → сравнение последовательности кадров с ожидаемой (хотя бы один маршрут полностью, остальные — на ключевых сценариях).
- **Шов 3 (квиз)**: существующая валидация банка покрывает новый модуль автоматически.
- **Шов 4 (фронт)**: рендер кадра нового Kind'а (обе разновидности: ячейки и узлы со стрелками), парсинг сценария операций, ошибки ввода. DOM ниже публичного API не трогаем.

## Out of Scope

- Двусвязный и циклический списки; расширенный API связного списка (Reverse, Sort и т.п.).
- Generics, конкурентный доступ, сериализация структур.
- Визуализация внутренней capacity и перевыделения backing array растущего List-слайса; адресов памяти узлов. Заданная ёмкость фиксированных Stack/Queue при этом отображается.
- Редактор сценариев с подсветкой синтаксиса, сохранение сценариев.
- Изменения транспорта SSE и плеера — инфраструктура трейсера не трогается.

# Модуль: «Хеш-таблицы с коллизиями» (Блок 1)

> Метка: `ready-for-agent`
> Статус: утверждена (Ч1 пройден), разбита на тикеты 15–16 (Ч2 пройден).

## Problem Statement

После линейных структур учащийся должен понять, как хранить пары «ключ — значение» и получать значение по ключу, не перебирая всю коллекцию. Важная часть темы — коллизии: разные ключи могут попасть в один bucket, и реализация должна разрешить столкновение и сохранить доступность обеих записей. Готовый `map` Go скрывает эти механизмы, поэтому нужна собственная небольшая реализация с наблюдаемыми шагами.

## Solution

Добавить учебную хеш-таблицу в общий пакет структур. Используется таблица фиксированного числа buckets с разрешением коллизий методом цепочек: bucket хранит несколько пар ключ-значение. Реализация работает в quiet mode и может выдавать типизированные события. Визуализатор принимает сценарий операций и рисует buckets с цепочками, а квиз закрепляет хеширование, коллизии и сложность операций.

## User Stories

1. As a учащийся, I want to хранить пары целочисленных ключей и значений в собственной таблице, so that понять базовую абстракцию «ключ — значение» без скрывающего детали `map`.
2. As a учащийся, I want to выбирать положительное число buckets, so that наблюдать, как ёмкость bucket-массива влияет на распределение ключей.
3. As a учащийся, I want to добавлять пару по ключу и обновлять значение уже существующего ключа, so that один ключ соответствовал ровно одной актуальной записи.
4. As a учащийся, I want to искать ключ и различать найденное значение и промах, so that понимать поведение lookup.
5. As a учащийся, I want to удалять ключ, сохраняя остальные записи той же цепочки, so that увидеть, как удаление работает при коллизиях.
6. As a учащийся, I want to наблюдать вычисление bucket-индекса и обход цепочки, so that видеть цену поиска при удачном распределении и при коллизиях.
7. As a учащийся, I want to прогонять текстовый сценарий `put`, `get`, `delete`, so that разбирать собственные примеры без изменения кода.
8. As a учащийся, I want to видеть все buckets и цепочки ключ-значение в каждом кадре, so that сравнивать пустые buckets, одиночные записи и несколько столкнувшихся ключей.
9. As a учащийся, I want to читать пояснение к каждому шагу, включая обновление, найденный ключ и промах, so that связывать картинку с операцией.
10. As a учащийся, I want to пользоваться таблицей как обычной Go-структурой без визуального слоя, so that проверять её поведение в quiet mode и переиспользовать библиотечный API.
11. As a учащийся, I want к типизированным событиям операций, so that Frame Renderer строил кадры, не зная внутреннего устройства алгоритма.
12. As a учащийся, I want проверить себя квизом по коллизиям, цепочкам, buckets и ожидаемой/худшей сложности, so that закрепить компромиссы структуры.

## Implementation Decisions

- **Пакет и границы**: `algorithms/structures`, как для линейных структур. Алгоритм не импортирует `visual/` и `quiz/`; сохраняются ADR-0001–0003 и существующий транспорт SSE.
- **Учебный контракт**: человек пишет черновик HashTable до реализации библиотечного тикета (`автор-черновик: человек`). Агент дорабатывает его по итогам ревью, не переписывая молча.
- **Тип данных**: целочисленный ключ и целочисленное значение; generics и произвольные типы ключей не входят в начальную реализацию.
- **Модель**: фиксированное положительное число buckets; коллизии разрешаются отдельными цепочками. Функция для целочисленного ключа — остаток от деления на число buckets с нормализацией отрицательного остатка в диапазон индексов. Например, при пяти buckets ключи `1` и `6` попадают в один bucket. Модель выбрана, чтобы механизм коллизий был детерминированным и видимым.
- **Минимум API**: создание таблицы, `Put(key, value)`, `Get(key)` с результатом и признаком наличия, `Delete(key)` с признаком удаления и `Len()`. Повторный `Put` существующего ключа обновляет значение и не увеличивает длину. Неуспешный `Get`/`Delete` — обычный промах, не ошибка. Отрицательное или нулевое число buckets при создании возвращает ошибку, не панику.
- **Изоляция темы**: таблица не растёт и не выполняет rehash; число buckets задаётся при создании. Это оставляет фокус на bucket-индексе, коллизиях и обходе цепочек. Вставка, поиск и удаление затрагивают только выбранный bucket.
- **События**: собственные типизированные события описывают выбранный bucket, посещение записи цепочки, вставку/обновление/удаление и результат поиска (найдено/не найдено). Событий достаточно, чтобы восстановить смысл каждого шага; алгоритм не создаёт текстовые UI-логи.
- **Визуальный контракт**: сценарий — по одной операции на строку: `put <key> <value>`, `get <key>`, `delete <key>`. Пользователь задаёт число buckets. Ошибки синтаксиса, целых чисел и конфигурации сообщаются до Run; промахи `get` и `delete` показываются как успешные шаги сценария.
- **Кадры**: каждый кадр — полный самодостаточный снимок (ADR-0002), содержащий число buckets, записи каждой цепочки, подсветки выбранного bucket/посещённой/изменённой записи, надгробия удалённых на этом шаге записей (ключ, значение и бывшая позиция в цепочке — сам снимок корзин их уже не содержит), имя операции и пояснение на русском. Для отдельной формы bucket-массива используется новый `kind` кадра `hash-table`, чтобы не менять контракт `kind="structure"` линейных структур.
- **Сервер и фронтенд**: тонкий маршрут `/api/run/hash-table` повторяет существующий шаблон парсинг → валидация → `runStreaming`; общий SSE-транспорт не меняется. Фронтенд добавляет ввод сценария и рендер buckets с цепочками; существующие рендеры остаются рабочими.
- **Ограничения Run**: для визуализации — 1–100 buckets, не более 100 одновременно хранимых записей и не более 500 операций; frontend и сервер зеркально проверяют их до Run. Это лимиты одного визуального запуска, не библиотечной таблицы. На операцию приходится не более события выбора bucket, события на каждую посещённую запись и одного события результата/изменения; с максимум 100 записями и 500 операциями верхняя граница потока — 51 001 кадр (включая начальный). Удаление не добавляет кадр сверх события изменения: удалённая запись живёт в снимке этого же кадра надгробием на бывшей позиции. Событие выбора bucket несёт сырой остаток ключа — объяснение расчёта рендер собирает из события, не повторяя формулу библиотеки. Отдельного отсечения уже начатого SSE-потока нет.
- **Квиз**: модуль `hash-tables` в `block-1`, 5–8 вопросов в существующем формате. Темы: ключ/bucket/hash-индекс, коллизия, разрешение цепочками, обновление и удаление, средняя и худшая сложность, влияние распределения и заполненности buckets.
- **PROGRESS.md**: строка «Хеш-таблицы с коллизиями» отмечается только после завершения обязательных частей модуля.

## Testing Decisions

- Хороший тест проверяет внешнее поведение и публичные контракты, а не конкретную внутреннюю форму узлов/слайсов.
- **Шов 1 — публичный API**: поведение `Put`/`Get`/`Delete`/`Len`, пустая таблица, обновление существующего ключа, промахи, отрицательные ключи, ошибки размера и несколько ключей с одинаковым bucket-индексом; emitter-шпион проверяет значимую последовательность событий на сценарии с коллизией.
- **Шов 2 — SSE-эндпоинт**: известный сценарий с коллизией → чтение `/api/run/hash-table` → сравнение последовательности самодостаточных кадров, включая выбор bucket и обход цепочки.
- **Шов 3 — квиз**: существующая валидация Quiz Bank проверяет 5–8 вопросов и формат; движок не меняется, если его публичный контракт не затрагивается.
- **Шов 4 — фронтенд**: публичные функции проверяют разбор корректных и некорректных сценариев и рендер пустых buckets, цепочки с коллизиями, попадания и промаха. DOM ниже публичного рендерера не тестируем.
- **Prior art**: публичные тесты Stack/Queue/List/LinkedList, SSE-тесты маршрутов структур и frontend-тесты парсера сценария/рендерера; нового тестового шва не вводим.

## Out of Scope

- Открытая адресация, линейное/квадратичное пробирование и другие стратегии разрешения коллизий.
- Динамический рост таблицы, rehash и автоматическая настройка числа buckets.
- Generics, произвольные типы ключей/значений, пользовательские hash-функции, криптографическая стойкость.
- Параллельный доступ, сериализация и постоянное хранение.
- Изменения общего Frame/SSE-транспорта, плеера или уже существующих визуализаций.

## Further Notes

- Целочисленные ключи/значения, modulo-хеширование и метод цепочек подтверждены на Ч1. Термины модуля определены в `GLOSSARY.md`.
- Worktree и статус `in-progress` относятся к конкретному тикету и создаются только после Ч2.

# Модуль: «Простые сортировки» (Блок 1)

> Метка: `ready-for-agent`
> Статус: утверждена (Ч1 пройден), разбита на тикеты 19–22 (Ч2 пройден).

## Problem Statement

После хеш-таблиц учащийся должен увидеть, как сравнения и перестановки постепенно упорядочивают массив, и сравнить несколько базовых алгоритмов по числу шагов, сложности и устойчивости. Пока в проекте нет сортировки, которую можно запустить как обычный алгоритм, наблюдать в визуализаторе и закрепить квизом.

## Solution

Добавить три простых алгоритма сравнения — bubble sort, selection sort и insertion sort — для целочисленного слайса. Каждый алгоритм работает в quiet mode и может сообщать типизированные события. Визуализатор принимает массив и выбранный алгоритм, показывает сравнения и изменения массива кадр за кадром; квиз закрепляет механику и характеристики трёх алгоритмов.

## User Stories

1. As a учащийся, I want to отсортировать массив целых чисел каждым из трёх простых алгоритмов, so that сравнить их на одинаковом входе.
2. As a учащийся, I want to запускать сортировки как обычные библиотечные функции без визуализатора, so that проверять результат и переиспользовать алгоритмы.
3. As a учащийся, I want to видеть каждое сравнение элементов, so that понимать, как алгоритм выбирает следующий шаг.
4. As a учащийся, I want to видеть каждую перестановку или запись значения в массив, so that связывать движение элементов с ходом алгоритма.
5. As a учащийся, I want к полному снимку массива на каждом кадре, so that использовать паузу и перемотку, не восстанавливая состояние из событий.
6. As a учащийся, I want to задавать массив с отрицательными числами и дубликатами, so that проверять сортировки на разнообразных данных.
7. As a учащийся, I want to наблюдать пустой, одноэлементный, уже отсортированный и обратный массивы, so that понимать граничные случаи и влияние начального порядка.
8. As a учащийся, I want к пояснению на русском для каждого кадра, so that понимать сравнение, обмен или сдвиг без чтения исходного кода.
9. As a учащийся, I want пройти квиз по механике, сложности и устойчивости сортировок, so that закрепить различия между алгоритмами.

## Implementation Decisions

- **Объём модуля**: bubble sort, selection sort и insertion sort. Merge sort и quicksort — следующий отдельный модуль по программе, не входят в этот тикетный набор.
- **Данные и порядок**: вход — `[]int`; результат упорядочен по возрастанию. Предлагаемый контракт библиотеки — сортировать переданный слайс на месте; пустой и одноэлементный слайсы допустимы. Дубликаты и отрицательные числа поддерживаются.
- **Варианты алгоритмов**: bubble sort завершает проходы досрочно, если обменов не было; selection sort выбирает минимум оставшейся части и меняет его с её первым элементом; insertion sort сдвигает только элементы, строго большие ключа. Это сохраняет устойчивость bubble/insertion и неустойчивость стандартного варианта selection.
- **Библиотека**: функции живут в `algorithms/sort`, не зависят от `visual/` и `quiz/`, работают в quiet mode и опционально принимают общий Emitter с типизированными событиями сравнения и изменения массива (ADR-0001). # Модуль: «Merge sort и quicksort» (Блок 1)

> Метка: `ready-for-agent`
> Статус: утверждена (Ч1 пройден), разбита на тикеты 26–28 (Ч2 пройден).

## Problem Statement

Учащийся уже сравнил простые сортировки, но ещё не видел два алгоритма, которые используют рекурсивное разбиение задачи и обычно масштабируются лучше квадратичных методов. Ему нужно понять, как merge sort разделяет массив и сливает отсортированные части, а quicksort выбирает pivot и распределяет относительно него элементы — и как эти решения влияют на порядок шагов, устойчивость, память и худший случай.

## Solution

Добавить merge sort и quicksort как следующий модуль блока 1: оба доступны как обычные библиотечные алгоритмы и как визуальные SSE-сценарии на том же входе-массиве, что и простые сортировки. Полные кадры показывают разделение/слияние для merge sort и pivot/partition для quicksort. Квиз закрепляет механику, сложность, дополнительную память и устойчивость выбранных вариантов.

## User Stories

1. As a учащийся, I want to запускать merge sort и quicksort на одном и том же массиве, so that сравнить два способа divide-and-conquer-сортировки.
2. As a учащийся, I want to вызывать каждый алгоритм как обычную библиотечную функцию без визуализатора, so that переиспользовать его и проверять результат отдельно от UI.
3. As a учащийся, I want to видеть, как merge sort делит диапазон на меньшие части и сливает отсортированные результаты, so that понимать рекурсивную структуру алгоритма.
4. As a учащийся, I want to видеть сравниваемые значения и записи при слиянии, so that понимать, откуда берётся каждое значение в итоговом массиве.
5. As a учащийся, I want to видеть выбранный pivot quicksort и текущую partition, so that понимать, почему элементы переходят в левую или правую часть.

7. As a учащийся, I want to задавать отрицательные числа и дубликаты, so that видеть, как оба алгоритма обрабатывают повторяющиеся значения.
8. As a учащийся, I want to запускать пустой, одноэлементный, отсортированный и обратный массивы, so that понимать граничные случаи и влияние входного порядка.

## Implementation Decisions

- **Объём модуля**: merge sort и quicksort — одна следующая тема после простых сортировок. Другие алгоритмы сортировки в этот модуль не входят.
- **Данные и результат**: вход — `[]int`, сортировка по возрастанию на месте с точки зрения вызывающего кода; пустой и одноэлементный слайсы допустимы, отрицательные значения и дубликаты поддерживаются.
- **Merge sort (предлагаемый вариант)**: рекурсивный top-down divide-and-conquer слияния; стабильный — при равенстве первым выбирается значение из левой части. Для слияния допускается вспомогательная память O(n); результирующий порядок записывается обратно во входной слайс. Сложность — O(n log n) во всех случаях.
- **Quicksort (предлагаемый вариант)**: in-place partition по схеме Lomuto с последним элементом диапазона как pivot; элементы строго меньше pivot переходят в левую часть, затем pivot занимает финальную позицию. Вариант неустойчив; средняя сложность O(n log n), худшая O(n²), в частности на уже упорядоченных входах при выбранном pivot. Переполнение рекурсией/стеком в худшем случае — предмет тестирования в пределах визуального лимита, не отдельная оптимизация.
- **Библиотека**: оба алгоритма живут в `algorithms/sort`, не зависят от `visual/` и `quiz/`, работают в quiet mode и опционально принимают Emitter с типизированными событиями. События достаточно подробны, чтобы показать сравнения, слияние/запись и pivot/partition/обмен; точные типы и последовательности закрепляются тикетами.
- **Визуализация**: новые маршруты используют общий контракт входа простых сортировок, включая отказ от невалидного входа до SSE и лимит 100 элементов. Каждый запуск начинается с исходного кадра, затем идёт кадр на событие.
- **Кадры и UI**: используется существующий `kind="sort"` и полный снимок всего массива; контракт и рендеринг bubble/selection/insertion не ломаются. Новые кадры дополнительно показывают активный диапазон/части для merge sort и pivot/границы partition для quicksort, с алгоритм-специфичными ролями подсветки и русскими пояснениями. Расширение payload допустимо только если оно обратно совместимо с существующими сортировками.
- **Транспорт и плеер**: общий Frame/SSE-транспорт и плеер не меняются; остаётся односторонний SSE-поток полных кадров.
- **Квиз**: новый модуль `divide-and-conquer-sorts` в `block-1`, после `simple-sorts`, с 5–8 вопросами в существующем формате. Вопросы покрывают разделение/слияние, выбор pivot/partition, лучшую/среднюю/худшую сложность, дополнительную память и устойчивость именно выбранных вариантов.
- **PROGRESS.md**: «Merge sort и quicksort» отмечается только после завершения обязательных библиотечной реализации, тестов, визуализации и квиза.

## Testing Decisions

# Модуль: «Обходы бинарного дерева: in-order, pre-order, post-order и по уровням» (Блок 2)

> Метка: `completed`
> Статус: спека утверждена (Ч1); тикеты 31–33 завершены.

## Problem Statement

Первый модуль Блока 2 должен дать учащемуся общий способ исследовать бинарное дерево до реализации BST. На одном и том же дереве важно увидеть, как три порядка обхода в глубину отличаются моментом посещения текущего узла, а обход по уровням — тем, что сначала посещает все узлы одного уровня. Сейчас в проекте нет общей модели бинарного дерева, библиотеки обходов и визуализации дерева.

## Solution

Добавить в библиотеку общую модель бинарного дерева и четыре обхода: in-order, pre-order, post-order и обход по уровням. Каждый обход доступен как обычная функция и может эмитировать типизированные события. Визуализатор принимает произвольное бинарное дерево, выбранный порядок обхода и показывает посещение узлов на снимках дерева; для обхода по уровням кадры дополнительно показывают очередь. Квиз закрепляет различия порядков и их базовые характеристики.

## User Stories

1. As a учащийся, I want запустить четыре порядка обхода на одном бинарном дереве, so that сравнить порядок посещения узлов на одинаковой форме дерева.
2. As a Go-разработчик, I want пользоваться общей моделью бинарного дерева из библиотеки, so that следующий модуль BST мог строиться поверх неё.
3. As a учащийся, I want видеть in-order, pre-order и post-order на одном дереве, so that понять, когда текущий узел посещается относительно левого и правого поддеревьев.
4. As a учащийся, I want видеть обход по уровням и очередь узлов, so that понять, почему узлы посещаются уровень за уровнем.
5. As a учащийся, I want видеть текущий узел и уже посещённую последовательность, so that читать порядок обхода кадр за кадром.
6. As a учащийся, I want задавать деревья разной формы и с повторяющимися значениями, so that отличать идентичность узла от его значения и проверять несимметричные случаи.
7. As a Go-разработчик, I want запускать обходы в quiet mode без визуализатора, so that использовать их как обычные функции библиотеки.
8. As a учащийся, I want пройти квиз по порядкам обхода, очереди и сложности, so that закрепить тему перед реализацией BST.

## Implementation Decisions

- **Объём модуля**: обходы бинарного дерева — три обхода в глубину (in-order, pre-order, post-order) и обход по уровням. Операции BST, балансировка и обходы графов в модуль не входят.
- **Общая модель**: `algorithms/trees` вводит бинарный `Node` с целочисленным значением и левым/правым потомками. Отсутствующий потомок задаётся `nil`; дерево не обязано удовлетворять свойствам BST, повторяющиеся значения разрешены. Модель предназначена для повторного использования следующим модулем BST.
- **Контракт обходов**: каждый обход принимает корень дерева и возвращает значения в порядке посещения. Пустое дерево допустимо и даёт пустой результат. In-order рекурсивно посещает левое поддерево, текущий узел, правое поддерево; pre-order — текущий узел, левое, правое; post-order — левое, правое, текущий. Обход по уровням использует FIFO-очередь и посещает узлы слева направо внутри каждого уровня.
- **События**: обходы работают в quiet mode и опционально принимают общий Emitter (ADR-0001). События позволяют восстановить посещаемый узел и последовательность; события обхода по уровням дополнительно предоставляют состояние очереди, необходимое для кадров. Идентичность узла не выводится из значения: значения могут повторяться. Точные типы событий и их гранулярность фиксируются в библиотечном тикете.
- **Ввод визуализатора**: пользователь передаёт вложенный JSON с полями `value`, `left` и `right`; отсутствующий или `null` потомок означает пустую ветвь, верхний `null` — пустое дерево. На Run выбирается один из четырёх порядков обхода. Некорректный JSON и превышение лимита отклоняются до начала SSE.
- **Лимит визуального Run**: не более 100 узлов на запуск; это предел для обозримой визуализации и размера потока, а не ограничение библиотечной модели или функций обхода. Лимит проверяется сервером и фронтендом до запуска.
- **Кадры**: новый `kind="tree"` содержит полный снимок узлов и связей, идентификатор активного узла, уже посещённые узлы с порядковыми номерами и пояснение на русском. Идентификаторы узлов стабильны внутри дерева и не зависят от значения (например, могут задаваться путём от корня). Для обхода по уровням кадр содержит очередь. Запуск начинается с исходного кадра, далее кадры строятся по событиям; общий SSE-транспорт и плеер не меняются. Вид дерева проектируется так, чтобы его можно было переиспользовать модулем BST.
- **Сервер и фронтенд**: тонкий маршрут запуска принимает дерево и выбранный порядок обхода; фронтенд проверяет JSON до Run и отображает кадры дерева. Точные имена маршрута и поля запроса определяются тикетом, общий транспорт не меняется.
- **Квиз**: добавить `block-2` («Блок 2. Деревья») и модуль `tree-traversals` первым в этом блоке, с 5–8 вопросами в существующем формате. Вопросы покрывают последовательность посещения на заданном дереве, различие трёх порядков в глубину, очередь при обходе по уровням, время O(n) и вспомогательную память DFS/BFS на базовом учебном уровне.
- **PROGRESS.md**: строка «Обходы (in / pre / post / по уровням)» отмечается только после завершения обязательных библиотечных реализаций, тестов, визуализации и квиза.

## Testing Decisions

# Модуль: «BST: вставка, поиск и удаление» (Блок 2)

> Метка: `ready-for-agent`
> Статус: спека утверждена (Ч1); тикеты 34–37 утверждены (Ч2).

## Problem Statement

Модуль обходов ввёл общую модель бинарного узла, но не структуру, которая поддерживает поиск по упорядоченным ключам. По программе учащийся должен реализовать BST, прежде чем переходить к концептуальному разбору балансировки.

## Solution

Добавить в `algorithms/trees` операции вставки, поиска и удаления в обычном бинарном дереве поиска. Учащийся задаёт сценарий операций и видит сравнения, переходы по ветвям и изменения дерева; квиз закрепляет инвариант BST, случаи удаления и сложность.

## User Stories

1. As a Go-разработчик, I want вставлять, искать и удалять целочисленные ключи в BST, so that пользоваться упорядоченным бинарным деревом без визуализатора.
2. As a учащийся, I want видеть сравнения и переходы влево или вправо, so that понимать, как BST сокращает область поиска.
3. As a учащийся, I want наблюдать удаление листа, узла с одним ребёнком и узла с двумя детьми, so that понимать, как после удаления сохраняется BST-инвариант.
4. As a учащийся, I want видеть сложность `O(h)` и её худший случай `O(n)`, so that не считать несбалансированное BST гарантированно логарифмическим.
5. As a учащийся, I want пройти квиз по инварианту, операциям и удалению, so that закрепить тему перед концептуальной балансировкой.

## Implementation Decisions

- **Общая модель**: операции BST переиспользуют `trees.Node` и существующий пакет `algorithms/trees`; обычные бинарные деревья обходов по-прежнему не обязаны быть BST.
- **Инвариант и дубликаты**: ключи — целые числа; для каждого узла все значения левого поддерева строго меньше его значения, правого — строго больше. Вставка существующего значения не меняет дерево и сообщает, что новый узел не добавлен.
- **Поиск**: пустое дерево и отсутствующий ключ допустимы и дают результат «не найден», а не ошибку входа.
- **Удаление**: отсутствующий ключ не меняет дерево и сообщает, что удаление не выполнено. Удаление поддерживает лист, узел с одним ребёнком, узел с двумя детьми и корень; для двух детей используется inorder-successor (минимум правого поддерева). Контракт позволяет вернуть новый корень после операции.
- **События**: quiet mode и типизированные события используют одну семантику (ADR-0001). Событий достаточно, чтобы восстановить сравнения/переходы, исход операции и структурные изменения, включая поиск successor и удаление узла-преемника. Детальная гранулярность событий фиксируется библиотечным тикетом.
- **Ввод визуализатора**: `GET /api/run/bst` принимает параметр `script`. Run начинается с пустого дерева; сценарий задаёт по одной команде на строку: `insert N`, `search N`, `delete N`. Пустые строки игнорируются; нужен хотя бы один непустой шаг. Значения — десятичные целые в безопасном диапазоне JavaScript (от `-(2^53−1)` до `2^53−1`). Дубликат при вставке и промахи поиска/удаления — допустимые операции, а не ошибки сценария. Произвольное вложенное дерево не принимается как исходное BST.
- **Лимиты визуального Run**: не более 100 живых узлов и 500 команд за запуск; это ограничения размера визуализации и потока кадров, не библиотеки. Некорректный сценарий и превышение лимитов отвергаются до SSE; сервер и фронтенд зеркально валидируют синтаксис, число и диапазон значений.
- **Кадры**: `kind="tree"` показывает полный актуальный снимок дерева, активный узел/путь сравнения, пояснение операции и текущий результат. Поле `order` снимка несёт значение `"bst"` — не порядок обхода, а маркер семейства кадров сценария BST в контракте TreeSnapshot; `visited` и `queue` в таких кадрах всегда пустые. После структурного изменения снимок содержит новую топологию и корень. Идентификатор узла — путь от корня в пределах текущего кадра; стабильная идентичность между кадрами не обещается. Для удаления с двумя детьми кадры показывают выбор successor и итоговое изменение дерева. Общий SSE-транспорт и плеер не меняются.
- **Сервер и фронтенд**: `GET /api/run/bst` принимает сценарий BST; структура кадров фиксируется визуальными тикетами. Фронтенд зеркально проверяет сценарий до Run и переиспользует рендер дерева, не меняя поведение обходов.
- **Квиз**: в `block-2` добавить `bst` после `tree-traversals`, с 5–8 вопросами в существующем формате. Вопросы покрывают инвариант, повторную вставку, поиск/промах, все три случая удаления, inorder-successor и сложность `O(h)` с худшим случаем `O(n)`.
- **PROGRESS.md**: пункт «BST — реализовать» отмечается только после завершения библиотечной части, визуализации, тестов и квиза.

## Testing Decisions

- **Шов 1 — публичный API**: проверяются инвариант после последовательностей операций, пустое дерево, успешные и неуспешные вставка/поиск/удаление, дубликат, удаление корня и все три структурных случая. Событийные тесты проверяют наблюдаемую последовательность сравнений и структурных изменений.
- **Шов 2 — SSE-эндпоинт**: проверяются известные сценарии вставки, поиска и удаления, включая successor, полный актуальный снимок после изменений и финальное дерево; некорректный ввод и превышение лимитов отвергаются до SSE.
- **Шов 3 — фронтенд визуализатора**: публичные функции проверяют сценарий, URL запуска и рендер снимков/активного пути; существующая визуализация обходов остаётся совместимой.
- **Шов 4 — Quiz Bank**: существующая валидация проверяет формат 5–8 вопросов и ровно один правильный ответ; тесты проверяют порядок модулей `block-2`.
- Новые общие тестовые швы не вводятся.

## Out of Scope

- AVL, красно-чёрные и иные самобалансирующиеся деревья, повороты и гарантированное `O(log n)`.
- Повторяющиеся ключи в BST, пользовательские компараторы и обобщённые типы.
- Произвольный JSON-редактор BST, сохранение сценариев и изменения общего SSE-транспорта/плеера.

# Модуль: «Trie: вставка, поиск, префиксы и удаление» (Блок 2)

> Метка: `ready-for-agent`
> Статус: спека утверждена (Ч1); тикеты 40–43 утверждены (Ч2).

## Problem Statement

После обзорного модуля B-деревьев учащийся возвращается к реализуемым структурам: по программе нужно реализовать trie — префиксное дерево поверх строк. BST уже показал поиск по упорядоченным целочисленным ключам, но не показывал структуру, в которой путь от корня сам кодирует ключ, а общие префиксы слов разделяются и переиспользуются. В библиотеке нет работы со строковыми ключами и нет визуализации дерева произвольного ветвления.

## Solution

Добавить в `algorithms/trees` классический несжатый Trie для Unicode-слов: переходы по отдельным rune, узел помечается как конец слова. Библиотека работает в quiet mode и опционально эмитирует типизированные события. Визуализатор принимает сценарий команд и показывает пошаговый обход по rune, повторное использование и создание рёбер и очистку ставших ненужными узлов при удалении; квиз в `block-2` после `b-trees` закрепляет механику и сложность.

## User Stories

1. As a учащийся, I want вставлять Unicode-слова в Trie и видеть, как общие префиксы разделяются, so that понимать, что путь от корня кодирует слово.
2. As a учащийся, I want различать поиск точного слова и проверку префикса, so что понимать разницу между «слово сохранено» и «есть слово с таким началом».
3. As a учащийся, I want удалять слово и наблюдать, что стираются только больше не нужные узлы, so that увидеть pruning и сохранение общих префиксов.
4. As a Go-разработчик, I want пользоваться Trie как обычной библиотечной структурой без визуализатора, so что проверять поведение в quiet mode и переиспользовать её вне проекта.
5. As a учащийся, I want к типизированным событиям операций, so что Frame Renderer строил кадры по шагам обхода по rune, не зная внутренностей структуры.
6. As a учащийся, I want задать сценарий `insert`/`search`/`prefix`/`delete` и прогнать его в визуализаторе, so что разбирать собственные примеры без изменения кода.
7. As a учащийся, I want видеть в кадре ветвление на любое число rune-переходов, отметки конца слова и активный путь, so that взгляд сразу цеплялся за действие операции.
8. As a учащийся, I want пройти квиз по Trie, so что закрепить rune-переходы, поведение дубликатов, различие Search и StartsWith, pruning и сложность операций.

## Implementation Decisions

- **Пакет и границы**: `algorithms/trees` — классический несжатый Trie, рядом с BST и обходами. Алгоритм не импортирует `visual/` и `quiz/`; сохраняются ADR-0001–0003 и существующий транспорт SSE.
- **Учебный контракт**: черновик Trie пишет пользователь (`автор-черновик: человек` в тикете 40). Агент дорабатывает его по итогам ревью, не переписывая молча; реализация тикета 40 не начинается до появления и явного подтверждения черновика на Ч2.5.
- **Ключи и сравнение**: слова — непустые строки Unicode в валидном UTF-8, то есть последовательности Unicode scalar values; библиотечная операция с невалидным UTF-8 (например, string([]byte{0xFF})) отклоняется различимым результатом-ошибкой — не Search-промахом (not-found) и не StartsWith-«найденным префиксом» (prefix-found); Trie и Len при этом не меняются, событий нет. Точные Go-сигнатуры и формы ошибок для невалидного UTF-8 следуют пользовательскому черновику — он обязан допускать такой различимый результат — и подтверждаются на Ч2.5 до реализации. Каждый шаг пути — одна руна (одно Unicode scalar value; переходы не по байтам и не по code units). Сравнение rune точное: без нормализации Unicode и без смены регистра — слова, различающиеся только регистром или формой символов, считаются разными. Узел помечается флагом конца слова; отметка не означает, что узел — лист.
- **Минимум API**: Insert (добавление слова), Search (точное слово), StartsWith (проверка существования пути префикса в Trie: идёт ли от корня путь по rune префикса, независимо от того, образует ли он конец слова), Delete (удаление слова) и Len (число разных слов). Повторная вставка идемпотентна: дерево и Len не меняются, результат сообщает, что слово не добавлено. Промах Delete — не ошибка: дерево не меняется, результат сообщает, что слово не найдено и не удалено. Пустое слово запрещено: Insert и Delete от пустого слова возвращают ошибку; Search("") — всегда false; StartsWith("") — всегда true: пустой префикс соответствует корню, в том числе в пустом Trie. Эти гарантии пустого запроса относятся к инициализированному Trie: валидный пустой Trie создаёт `NewTrie()`; nil-приёмник и нулевое значение `Trie{}` — неинициализированный Trie: операции с ошибочным результатом отклоняются ошибкой `ErrUninitializedTrie` до проверки входа и до любых событий, `Len()` возвращает 0. Точные Go-сигнатуры и формы результатов следуют пользовательскому черновику: утверждаются на Ч2.5 и после утверждения фиксируются в тикете 40 до реализации; семантика методов, описанная здесь, обязательна и сигнатурами не ослабляется.
- **Pruning**: Delete стирает только узлы, которые после удаления больше не ведут ни к какому концу слова; ветвления и узлы на путях к другим словам (включая сохранённые слова-префиксы более длинных слов) остаются.
- **События**: quiet mode и типизированные события одной семантики (ADR-0001). Событий достаточно, чтобы визуально показать пошаговый обход по rune, повторное использование или создание ребра, отметку конца слова и pruning. Гранулярность: каждое rune-обращение даёт не более одного события посещения/проверки — событие несёт состояние ребра: `reused` для существующего ребра, `created` для нового ребра, создаваемого вставкой; вставка всегда проверяет все rune слова и после создания отсутствующего ребра с состоянием `created` продолжает обход; ограничение «до первой отсутствующей rune включительно» относится только к попыткам поиска/проверки префикса/удаления пройти отсутствующее ребро — последнее событие проверки несёт состояние `missing` и проверяемую rune, узел не создаёт; на последней rune вставки/удаления то же событие несёт итоговое состояние флага конца слова, и только когда оно меняется (отдельного события отметки конца слова нет); не более одного события на каждый узел pruning; каждая валидная команда/вызов — ровно одно событие результата. Удаление снимает флаг конца слова в последнем событии посещения удаляемого слова. No-op-последовательности определены точно: повторный Insert — события посещения на все rune слова (по одному на проверенное rune-ребро, состояния `reused`) и ровно одно событие результата `already-existed`; флаг конца слова уже установлен и не меняется, pruning нет. Промах Search/Prefix/Delete по отсутствующему ребру — события посещения/проверки до первой отсутствующей rune включительно (последнее событие — проверка с состоянием `missing` и проверяемой rune) и ровно одно событие результата (`not-found` / `prefix-not-found` / `not-deleted`); мутаций и pruning нет. Промах Search/Delete по полностью существующему пути, конечный узел которого не отмечен как конец слова (например, delete `ab` при сохранённом `abc`), — события посещения на все rune слова и ровно одно событие результата (`not-found` / `not-deleted`); флаг конца слова и pruning не меняются. Пустые Search("") и StartsWith("") валидны и дают ровно одно событие результата (`not-found` / `prefix-found`) без событий посещения; пустые Insert("") и Delete("") невалидны и возвращают ошибку до любых событий — без событий посещения и результата. Точные типы и сигнатуры событий фиксируются тикетом 40.
- **Ввод визуализатора**: сценарий по одной команде на строку: `insert W`, `search W`, `prefix W`, `delete W`. Аргумент команды — один непустой Unicode-токен без пробелов из валидного UTF-8 (последовательность Unicode scalar values); аргумент с невалидным UTF-8 — например, сыро закодированный невалидный байт (`%FF`) — отвергается до начала SSE. Пустые строки и строки только из пробелов игнорируются, как в сценарии BST; сценарий без единой команды отклоняется. Run стартует с пустого Trie. Повторная вставка и промахи `search`/`prefix`/`delete` — допустимые шаги сценария с явным пояснением, а не ошибки запроса. Ошибки синтаксиса и аргумента сообщаются до Run.
- **Кадры**: отдельный `kind="trie"` — самодостаточные снимки (ADR-0002) с произвольным ветвлением (число rune-переходов узла не ограничено двумя), отметками конца слова и активным путём текущей операции; имя операции и пояснение на русском. Поле `result` — часть снимка Trie внутри `Frame.Data` (не поле верхнего Frame envelope): в стартовом кадре и во всех промежуточных кадрах посещения/проверки/pruning до события результата — ровно `result: null`; лишь кадр результата операции — последний кадр команды, строящийся по её отдельному событию результата, — несёт одно значение закрытого множества: `insert` / `already-existed`, `found` / `not-found`, `prefix-found` / `prefix-not-found`, `deleted` / `not-deleted` — итог читается из снимка без пересчёта. Поле `edgeCheck` — тоже часть снимка Trie внутри `Frame.Data`: в каждом кадре посещения/проверки rune — при состояниях `reused`, `created` и `missing` — объект `{ rune: <JSON-строка ровно из одной rune (Unicode scalar value), не числовой код>, state: "reused" | "created" | "missing" }`; во всех остальных кадрах — стартовом, промежуточных pruning и в кадре результата операции — ровно `edgeCheck: null`. При `reused`/`created` активный путь доходит до существующего/созданного потомка; при `missing` (только поиск/проверка префикс/удаление) активный путь содержит только существующие узлы — до родителя отсутствующего ребра, а отсутствующий потомок не добавляется в топологию и не имеет идентификатора узла: попытка видна через `edgeCheck.rune` отдельно. Идентификатор узла в снимке — frame-local путь от корня по rune-меткам рёбер в каноническом кодировании: `root` для корня, далее по одному сегменту на rune — `U+` плюс шестнадцатеричный код rune в верхнем регистре минимальной ширины 4 (длиннее при необходимости), разделитель `/` (например, `root/U+043F/U+0440` — путь первых двух rune слова «при»); представление уникально в пределах каждого снимка. Это отдельный контракт Trie-снимков, не переиспользующий L/R-контракт бинарного `NodeID`. Межкадровая стабильность идентификаторов не обещается; существующий бинарный `kind="tree"` (обходы, BST) не меняется.
- **Лимиты визуального Run** (численные значения — 500 команд, 100 rune в слове/префиксе, 100 живых rune-узлов — утверждены на Ч2; пиковая семантика лимита живых узлов принята на повторном Ч3): не более 500 команд, не более 100 rune в слове/префиксе, не более 100 живых rune-узлов (корень не считается). Лимит живых узлов применяется к пиковому размеру Trie: максимум числа живых узлов по состоянию после каждой команды сценария, а не только к финальному состоянию; сервер и TS dry-run применяют одну семантику проверки. Это safety bounds одного визуального запуска ради обозримого дерева и размера потока, а не пределы библиотечного Trie. Сервер и фронтенд зеркально валидируют сценарий и лимиты до начала SSE; фронтенд перед Run симулирует сценарий (dry-run) и считает пиковое число живых rune-узлов, сервер проверяет лимит до SSE. Гранулярность событий нормативно зафиксирована в разделе «События» выше: не более одного события посещения/проверки на rune-обращение (с состоянием ребра — `reused` / `created` / `missing` — и, при изменении, флагом конца слова в последнем событии посещения), не более одного события на каждый узел pruning и ровно одно событие результата на валидную команду; при этой гранулярности пределы ограничивают размер потока. Консервативная верхняя граница потока — 500 операций × (до 100 rune-переходов и проверок + до 100 узлов pruning + 1 результат) + 1 стартовый кадр = 100 501 кадр: событие проверки отсутствующего ребра входит в лимит rune-переходов и проверок на команду и не считается сверх длины; отдельного отсечения уже начатого SSE-потока нет.
- **Сервер и фронтенд**: тонкий маршрут `GET /api/run/trie` повторяет шаблон парсинг → валидация → runStreaming; общий SSE-транспорт и плеер не меняются. Фронтенд добавляет ввод сценария и рендер Trie-снимков; существующие визуализации продолжают работать.
- **Квиз**: модуль `trie` в `block-2` после `b-trees`, 5–8 вопросов в существующем формате. Темы: rune-переходы и точное сравнение, идемпотентность повторной вставки, различие Search и StartsWith, поведение пустого слова, pruning при удалении, сложность операций O(m) — длина слова/префикса.
- **PROGRESS.md**: пункт «Trie — реализовать» отмечает только оркестратор после подтверждения пользователем мержа всех обязательных тикетов модуля (40–43, включая тикет квиза); имплементоры тикетов `PROGRESS.md` не меняют — синхронно с тикетом 43.

## Testing Decisions

- Новых швов нет — модуль ложится на существующие четыре; prior art — BST и модуль структур/хеш-таблицы.
- **Шов 1 — публичный API**: пустой Trie, однословный, разветвлённые и общие префиксы; дубликат вставки, промахи Search/StartsWith/Delete, поведение пустого слова (ошибки Insert/Delete, Search("") == false, StartsWith("") == true), удаление слова-префикса более длинного слова и более длинного слова с сохранением префикса, Len после серий операций. Точное сравнение подтверждается тестами: слова, различающиеся только регистром и/или NFC/NFD-последовательностью rune, остаются различными. Emitter-шпион проверяет точные последовательности событий, включая no-op-операции: повторный Insert — события посещения на все rune слова и ровно одно событие результата `already-existed`, без изменения флага конца слова и без событий pruning; промахи Delete, Search и StartsWith по отсутствующему ребру — события посещения/проверки до первой отсутствующей rune включительно (последнее событие — проверка с состоянием `missing` и проверяемой rune) и ровно одно событие результата (`not-deleted` / `not-found` / `prefix-not-found`); промахи Delete и Search по полностью существующему пути, конечный узел которого не отмечен как конец слова (например, delete `ab` при сохранённом `abc`), — события посещения на все rune слова и ровно одно событие результата, без изменения флага конца слова и без событий pruning; пустые Search("") и StartsWith("") — ровно одно событие результата со значениями `not-found` и `prefix-found` соответственно, без событий посещения; пустые Insert("") и Delete("") — ошибка до любых событий. Состояния рёбер в событиях сверяются на тестах: `created` при вставке в пустой Trie, `reused` при вставке второго слова по общему префиксу, `missing` при промахах поиска/префикса/удаления. Rune вне базовой многоязычной плоскости (например, `😀`, U+1F600) считаются одной rune (одно Unicode scalar value): одно событие посещения/проверки на такую rune — тесты явно проверяют, что обход и события идут по rune, а не по UTF-8 байтам. Невалидный UTF-8 (например, string([]byte{0xFF})) отклоняется каждой библиотечной операцией до событий различимым результатом-ошибкой — не Search-промахом и не StartsWith-«найденным префиксом»; тесты фиксируют отсутствие мутаций (Trie и Len не меняются) и полное отсутствие событий; точные Go-сигнатуры и формы ошибок следуют пользовательскому черновику — он обязан допускать такой различимый результат — и подтверждаются на Ч2.5.
- **Шов 2 — SSE-эндпоинт**: известный сценарий с общим префиксом → чтение потока → сравнение последовательности самодостаточных кадров `kind="trie"`, включая активный путь, отметку конца слова и pruning; тесты проверяют идентификаторы узлов и поле `result` снимков Trie внутри `Frame.Data` по контракту: `result: null` в стартовом и промежуточных кадрах посещения/pruning, значение закрытого множества только в кадре результата операции. Тесты покрывают каждый вариант закрытого множества `result` отдельным случаем: `insert`, `already-existed`, `found`, `not-found`, `prefix-found`, `prefix-not-found`, `deleted`, `not-deleted`, включая no-op-значения — повторный Insert → `already-existed`, промах Delete → `not-deleted`, промах prefix → `prefix-not-found` — со сверкой промежуточных `data.result: null` и финального enum. No-op-сценарии проверяются на промахах по отсутствующему ребру (search, prefix, delete) и существующем пути, конечный узел которого не отмечен как конец слова (search, delete), со сверкой событий посещения/проверки и события результата; кадры сверяются по полю `edgeCheck` снимка Trie — одно имя и одна форма в JSON между бэкендом и фронтом: `edgeCheck: null` в стартовом, промежуточных pruning и кадре результата операции (тест-ассерты на каждый случай), объект `{ rune: <JSON-строка ровно из одной rune>, state }` в каждом кадре посещения/проверки — включая символы вне BMP: JSON-строка `edgeCheck.rune` для `😀` — ровно `😀`, а идентификатор узла — `root/U+1F600` (hex-код rune, не surrogate-половина `U+D83D`); синонимичного поля `status` нет; состояния `created` (вставка в пустой Trie), `reused` (второе слово по общему префиксу) и `missing` (промахи) покрыты; при `missing` активный путь содержит только существующие узлы — до родителя отсутствующего ребра, а отсутствующий потомок отсутствует в топологии и не имеет идентификатора узла; `data.result` остаётся `null` до кадра результата операции. Пустой аргумент команды отвергается до Run, поэтому empty-API случаи (Search("")/StartsWith("")/Insert("")/Delete("")) проверяются emitter-тестами библиотеки, а не сценарием. Пиковый лимит проверяется тестом: сценарий, чей пик живых rune-узлов превышает 100 при финальном состоянии ≤100, отвергается до SSE, как и превышение других лимитов; игнорирование пустых строк/строк из пробелов и отказ сценария без единой команды проверяются тестом; некорректный сценарий отвергается до SSE. Тест невалидного UTF-8: сыро закодированный невалидный байт (например, `%FF` в кодированном аргументе) отвергается до SSE без частично начатого потока. Граничный тест лимита длины аргумента (изолирован от лимита живых узлов): `search` с аргументом ровно из 100 повторных `😀` в пустом Trie принимается и доводится до кадра результата операции `not-found` — события проверки не создают узлов; аргумент из 101 `😀` отвергается до SSE; rune считается по Unicode scalar values, не по UTF-8 байтам.
- **Шов 3 — фронтенд визуализатора**: публичные функции проверяют разбор корректных и некорректных сценариев, построение URL и рендер снимков (ветвление, отметки конца слова, активный путь), включая идентификаторы узлов и `result` по контракту: `null` в стартовом и промежуточных снимках, enum закрытого множества только в кадре результата операции; рендер проверяется на каждом варианте `result`, включая кадры no-op-сценариев — промахи по отсутствующему ребру (search, prefix, delete) и существующий путь без отметки конца слова (search, delete) — с активным путём из существующих узлов и полем `edgeCheck` той же формы, что у бэкенда (`edgeCheck: null` в стартовых/pruning/result-кадрах, `{ rune: <строка ровно из одной rune>, state }` в кадрах посещения/проверки, включая кадр с `edgeCheck.rune: "😀"` и идентификатором узла `root/U+1F600`) и `result: null` до кадра результата операции. Публичная симуляция сценария (dry-run) проверяется тестами: пиковое число живых rune-узлов (корень не считается) и лимит в 100 зеркалят серверную проверку до Run, включая сценарий с пиком >100 и финалом ≤100. Подсчёт rune на фронте — по Unicode scalar values, не UTF-16 code units: `😀` — одна rune, UTF-16-пара не считается за две. Одиночная UTF-16 surrogate в разобранном аргументе (не Unicode scalar value, невалидная последовательность scalar values) отклоняется до сериализации и Run: encodeURIComponent бросает URIError на одиночную surrogate, URLSearchParams может молча заменить её на U+FFFD — явная проверка предшествует обоим кодированиям. Граничный тест лимита длины (изолирован от лимита живых узлов): `search` с аргументом ровно из 100 повторных `😀` в пустом Trie принимается и доводится до рендера кадра результата операции со `result: "not-found"` — живые rune-узлы остаются нулевыми (события проверки не создают узлов); аргумент из 101 `😀` отвергается до Run. DOM ниже публичного рендерера и `fetch` без инъекции не тестируем.
- **Шов 4 — Quiz Bank**: существующая валидация банка покрывает новый модуль автоматически; тесты проверяют наличие `trie` и порядок модулей Блока 2.
- Новых общих тестовых швов не вводится.
