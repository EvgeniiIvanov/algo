# WORKFLOWS.md — сценарии процессов разработки

Склейка поверх скиллов. Скиллы — отдельные инструменты (`to-spec`, `to-tickets`, `implement`, `code-review`, `diagnosing-bugs`); этот документ описывает **в каком порядке и по каким правилам** они применяются. Любая сессия агента следует одному из потоков ниже — выбор потока определяется типом работы, а не настроением.

Скилл `implement-spec` не входит в канонический поток этого репозитория — не используем его.

## Модель взаимодействия

- Автоматизация живёт **только в OpenCode** (профили в `.opencode/agents/`); VS Code — место, где человек пишет черновики алгоритмов/структур, не часть автоматизации.
- Каждая сессия начинается с `AGENTS.md` и этого файла; далее — тикет (`docs/tickets/`), релевантная часть `docs/SPEC.md` и только относящиеся к задаче записи ADR/`GLOSSARY.md` (см. AGENTS.md, Context задачи).
- Пользователь общается **только с одним агентом-оркестратором** (одна сессия = один оркестратор).
- Всю специализированную работу оркестратор делегирует **субагентам** (`implementor`, `reviewer`, опционально `tester`) — пользователь с ними не контактирует.
- Оркестратор сам не пишет код и не реализует тикеты: каждое изменение кода делает субагент `implementor` в worktree тикета. Оркестратор управляет потоком, спавнит субагентов, готовит чекпойнты.
- На каждом чекпойнте оркестратор **останавливается** и формулирует конкретное «прочитай X и реши Y». Продолжение — только после явного подтверждения пользователя.
- Всё остальное (lint, CI-проверки, статусы тикетов, PROGRESS.md, файлы) оркестратор делает **автоматически, без спроса**.

## Чекпойнты

| # | Что утверждает пользователь | Когда |
|---|------------------------------|-------|
| Ч1 | Спека модуля | После `to-spec`, до разбиения на тикеты |
| Ч2 | Разбиение на тикеты | После `to-tickets`, до старта реализации |
| Ч2.5 | Черновик алгоритма/структуры (учебный контракт) | До старта реализации соответствующего библиотечного тикета |
| Ч3 | Находки ревью (принять/отклонить) | После `code-review`, до фиксов |
| Ч4 | Мерж в `main` | После зелёного CI и закрытых находок; всегда только пользователь |

## Учебный контракт

Цель проекта — обучение, поэтому автоматизация ограничена:

- **Черновик алгоритма/структуры пишет пользователь** (в `algorithms/`, коряво — нормально) для каждого библиотечного тикета. Это чекпойнт **Ч2.5, и он блокирующий**: реализация библиотечного тикета не начинается, пока черновик не появился и пользователь его явно не подтвердил.
- Агент дорабатывает конкретный черновик по итогам ревью, пишет тесты, визуализацию, квиз-вопросы и обвязку по тикету.
- В тикете помечаем `автор-черновик: человек` — субагенты не переписывают черновик молча, правки только через находки ревью.
- Ответы на вопросы квиза пользователь проходит сам — квиз и есть проверка усвоения.

## Роли

- **Оркестратор** — основная сессия OpenCode (`orchestrator`, `.opencode/agents/orchestrator.md`). Следит за потоком, спавнит субагентов, ведёт статусы, останавливается на чекпойнтах. Код не пишет и тикеты не реализует.
- **Имплементор** — субагент `implementor` (`.opencode/agents/implementor.md`), работает в worktree тикета. Пишет код **и тесты** по тикету, гоняет локальные проверки, коммитит в свою ветку `ticket/...` после проверок; push — только с одобрением пользователя; мерж в `main` — никогда.
- **Ревьюер** — субагент `reviewer` (`.opencode/agents/reviewer.md`, read-only), пары свежих дочерних сеансов по осям Standards/Spec (см. Review process в AGENTS.md). Не правит чужой код, находки передаёт оркестратору.
- **Тестировщик** (`tester`) — **необязательная** оценка, ориентированная на риск (кросс-стек-изменения, значимое поведение, высокие цены регрессии). Субагент read-only: тестов не пишет (их пишет имплементор), может гонять `make test`. Не каждый тикет его заслуживает — решает оркестратор.

## Поток A. Полный модуль (алгоритм + визуализация + квиз)

1. `git pull` в основной папке, свежий `main`.
2. Спека (`to-spec`) → **Ч1**.
3. Тикеты (`to-tickets`) → **Ч2**.
4. Worktree: `git worktree add ../algo-<slug> -b ticket/NN-<slug>`. Дальше всю реализацию тикета выполняет субагент `implementor` в этом worktree.
5. Каждый библиотечный тикет: **пользователь пишет черновик алгоритма/структуры** → имплементор доводит этот вертикальный срез (тесты и нужная интеграция). До появления и подтверждения черновика (**Ч2.5**) реализация библиотечного тикета не стартует. Тикеты кадров/SSE, фронтенда и квиза реализует имплементор по их зависимостям.
6. Локальные проверки как в CI: `go build/vet/test`, `golangci-lint`, для фронтенда `pnpm install --frozen-lockfile` + lint/test/build. После проверок имплементор коммитит локально в свою ветку `ticket/...` и пушит её в origin (`git push origin ticket/...` разрешён ему автоматически); PR и мерж — только пользователь.
7. Ревью (`code-review`: две оси Standards + Spec двумя параллельными свежими дочерними сеансами субагента `reviewer`) → **Ч3**.
8. Фиксы (делает имплементор) → повторное ревью только дельтой; фикс поведенческого бага = регрессионный тест.
9. Оркестратор ведёт статус текущего тикета и закрывает принятые находки → **Ч4: мерж** (PR или из основной папки) — мержит только пользователь. `PROGRESS.md` отмечается только после мержа всех обязательных тикетов модуля.
10. После мержа тикета оркестратор, получив подтверждение мержа и одобрение пользователя на чистку, удаляет чистый worktree и локальную ветку тикета; тикет отмечается `done`. Этот цикл повторяется **на каждый тикет**, а не один раз на модуль. Когда завершён весь модуль — обновить `PROGRESS.md` и предложить ретро (`retro`).
11. Затем — шаг очистки бэклога (см. одноимённый раздел ниже): отдельный шаг между модулями, не часть учебного модуля.

## Поток B. Модуль «только квиз»

Как A, но: без спеки и Ч1 (есть чек-лист тем модуля), один микротикет, обычно один коммит в worktree, быстрое ревью. Пример: тикет 07 (рекурсия).

## Поток C. Баг-фикс

Без тикетов и спеки. Диагностика (`diagnosing-bugs`) → **сначала регрессионный тест, потом фикс** → ревью дельты. Worktree опционален для однофайлового фикса. Мерж — Ч4 как обычно.

## Поток D. Рефакторинг

Как A, но без спеки (есть тикет с мотивацией). Поведение не меняется — тесты при рефакторинге правятся только из-за смены интерфейсов, выноса общих каркасов тестов (обвязки) или прояснения/усиления ожиданий: ослаблять проверки (ассерты) и сокращать покрытие публичного поведения нельзя. Полный повторный ревью-прогон, если диф >30%.

## Шаг очистки бэклога (после завершённого модуля)

Отдельный шаг после каждого завершённого учебного модуля и до старта следующего. Он **не часть модуля** и не влияет на отметку его учебного контента в `PROGRESS.md` — модуль отмечается независимо от того, проведён ли разбор.

1. Оркестратор устраивает разбор записей `docs/BACKLOG.md`, накопившихся по ходу модуля.
2. По каждой записи — одно из решений: реализовать (поток D; связанные мелкие улучшения можно группировать в один тикет, независимые — отдельные тикеты), отбросить или превратить в обычный запланированный тикет.
3. Разобранные записи удаляются из `docs/BACKLOG.md`; нерешённых заметок не копим.

## Выбор потока

| Тип работы | Поток |
|------------|-------|
| Новый алгоритм/тема с визуализацией | A |
| Теоретическая тема (только вопросы квиза) | B |
| Что-то сломалось / регрессия | C |
| Улучшение структуры без смены поведения | D |

Разбор `docs/BACKLOG.md` — не отдельный поток, а шаг очистки бэклога между модулями (см. раздел выше); выбранная из него работа реализуется потоком D.

Сомнения между A и C/D — спросить пользователя, не решать молча.
