# WORKFLOWS.md — сценарии процессов разработки

Склейка поверх скиллов. Скиллы — отдельные инструменты (`to-spec`, `to-tickets`, `implement`, `code-review`, `diagnosing-bugs`); этот документ описывает **в каком порядке и по каким правилам** они применяются. Любая сессия агента следует одному из потоков ниже — выбор потока определяется типом работы, а не настроением.

## Модель взаимодействия

- Пользователь общается **только с одним агентом-оркестратором** (одна сессия = один оркестратор).
- Всю специализированную работу оркестратор делегирует **субагентам** (ревью, реализация подзадач) — пользователь с ними не контактирует.
- Оркестратор сам не пишет код от себя: он управляет потоком, спавнит субагентов, готовит чекпойнты.
- На каждом чекпойнте оркестратор **останавливается** и формулирует конкретное «прочитай X и реши Y». Продолжение — только после явного подтверждения пользователя.
- Всё остальное (тесты, lint, CI-проверки, статусы тикетов, PROGRESS.md, файлы) оркестратор делает **автоматически, без спроса**.

## Чекпойнты

| # | Что утверждает пользователь | Когда |
|---|------------------------------|-------|
| Ч1 | Спека модуля | После `to-spec`, до разбиения на тикеты |
| Ч2 | Разбиение на тикеты | После `to-tickets`, до старта реализации |
| Ч3 | Находки ревью (принять/отклонить) | После `code-review`, до фиксов |
| Ч4 | Мерж в `main` | После зелёного CI и закрытых находок; всегда только пользователь |

## Учебный контракт

Цель проекта — обучение, поэтому автоматизация ограничена:

- **Черновик алгоритма пишет пользователь** (в `algorithms/`, коряво — нормально). Это Ч2.5 внутри потока A: реализация тикета библиотеки не начинается, пока черновик не появился.
- Агент дорабатывает черновик по итогам ревью, пишет тесты, визуализацию, квиз-вопросы, обвязку.
- В тикете помечаем `автор-черновик: человек` — субагенты не переписывают черновик молча, правки только через находки ревью.
- Ответы на вопросы квиза пользователь проходит сам — квиз и есть проверка усвоения.

## Роли

- **Оркестратор** — основная сессия. Следит за потоком, спавнит субагентов, ведёт статусы, останавливается на чекпойнтах. Код не пишет.
- **Имплементор** — субагент (или оркестратор в режиме реализации внутри worktree). Пишет код по тикету, гоняет локальные проверки.
- **Ревьюер** — субагент из **отдельной чистой сессии** (см. Review process в AGENTS.md). Не правит чужой код, находки передаёт оркестратору.
- **Тестировщик** — не отдельная роль: тесты пишет имплементор вместе с кодом, на трёх швах (AGENTS.md, Conventions).

## Поток A. Полный модуль (алгоритм + визуализация + квиз)

1. `git pull` в основной папке, свежий `main`.
2. Спека (`to-spec`) → **Ч1**.
3. Тикеты (`to-tickets`) → **Ч2**.
4. Worktree: `git worktree add ../algo-<slug> -b ticket/NN-<slug>`.
5. Тикет библиотеки: **пользователь пишет черновик алгоритма** → имплементор доделывает (тесты, интеграция). Остальные тикеты (кадры, SSE, фронтенд, квиз) — имплементор.
6. Локальные проверки как в CI: `go build/vet/test`, `golangci-lint`, для фронтенда `pnpm install --frozen-lockfile` + lint/test/build.
7. Ревью (`code-review` из чистой сессии, две оси) → **Ч3**.
8. Фиксы → повторное ревью только дельтой; фикс поведенческого бага = регрессионный тест.
9. Статусы тикетов и `PROGRESS.md` — оркестратор обновляет сам → **Ч4: мерж** (PR или из основной папки).
10. После мержа: worktree и ветки удаляются, модуль отмечен, предложить ретро (`retro`).

## Поток B. Модуль «только квиз»

Как A, но: без спеки и Ч1 (есть чек-лист тем модуля), один микротикет, обычно один коммит в worktree, быстрое ревью. Пример: тикет 07 (рекурсия).

## Поток C. Баг-фикс

Без тикетов и спеки. Диагностика (`diagnosing-bugs`) → **сначала регрессионный тест, потом фикс** → ревью дельты. Worktree опционален для однофайлового фикса. Мерж — Ч4 как обычно.

## Поток D. Рефакторинг

Как A, но без спеки (есть тикет с мотивацией). Поведение не меняется — тесты не трогаем, кроме правок из-за смены интерфейсов. Полный повторный ревью-прогон, если диф >30%.

## Выбор потока

| Тип работы | Поток |
|------------|-------|
| Новый алгоритм/тема с визуализацией | A |
| Теоретическая тема (только вопросы квиза) | B |
| Что-то сломалось / регрессия | C |
| Улучшение структуры без смены поведения | D |

Сомнения между A и C/D — спросить пользователя, не решать молча.
