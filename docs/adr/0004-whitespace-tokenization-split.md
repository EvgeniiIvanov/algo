# Два набора whitespace-семантики токенизации на клиенте

Токенизация сценария Trie на фронтенде (`splitScenarioFields` в `visual/frontend/src/scenarioFields.ts`) зеркалит серверный `strings.Fields` (Go `unicode.IsSpace`), чтобы ошибки ввода ловились до Run и токен на клиенте совпадал с токеном на сервере (иначе BOM U+FEFF приклеился бы к токену на сервере). Шесть исторических парсеров сценариев (стек, очередь, список, односвязный список, хеш-таблица, BST — `splitLegacyScenarioFields`) намеренно держат прежнюю JS-семантику (`trim()` + разрез по `\s`): тикет 42 требует, чтобы прежние визуализации продолжали работать без изменения их поведения. Известные расхождения двух наборов ровно два и зафиксированы тестами (`visual/frontend/tests/scenarioFields.test.ts`): BOM U+FEFF пробельный только в JS, NEL U+0085 — только в Go.

## Considered Options

- Глобальная унификация под Go-семантику — отклонено: молча изменило бы разбор прежних сценариев (BOM перестал бы отделять токен, NEL перестал бы быть частью токена) и нарушило бы требование тикета 42 о сохранении поведения старых визуализаций.
- Глобальная унификация под JS-семантику — отклонено: клиент пропускал бы формы, которые серверный парсер Trie разобрал бы иначе (BOM приклеился бы к токену на сервере), — ловить такие ошибки до Run было бы нельзя.
