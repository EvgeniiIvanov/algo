# Два набора whitespace-семантики токенизации на клиенте

Токенизация сценария Trie на фронтенде (`splitScenarioFields` в `visual/frontend/src/scenarioFields.ts`) воспроизводит **семантику** серверного `strings.Fields` (Go `unicode.IsSpace`), чтобы ошибки ввода ловились до Run и токен на клиенте совпадал с токеном на сервере (иначе BOM U+FEFF приклеился бы к токену на сервере). Утверждение про `strings.Fields` касается именно серверных парсеров текста сценария, а не всех серверных хендлеров и роутов: шесть исторических парсеров сценария (стек, очередь, список, односвязный список, хеш-таблица, BST) вызывают `strings.Fields` напрямую, а сервер в Trie-хендлере сам `strings.Fields` не вызывает — Trie реализует эквивалентную семантику вручную в `visual/server/trie.go` — функциями `trieSplit3`/`trieSpaceSize` (включая нюанс, что невалидные байты поле не рвут). Шесть исторических парсеров сценариев (стек, очередь, список, односвязный список, хеш-таблица, BST — `splitLegacyScenarioFields`) намеренно держат прежнюю JS-семантику (`trim()` + разрез по `\s`): тикет 42 требует, чтобы прежние визуализации продолжали работать без изменения их поведения. Известные расхождения двух наборов ровно два и зафиксированы тестами (`visual/frontend/tests/scenarioFields.test.ts`): BOM U+FEFF пробельный только в JS, NEL U+0085 — только в Go.

Последствия для шести исторических парсеров (сервер остаётся авторитетным и перепроверяет ввод):

- Команда, разделённая BOM (например «insert\uFEFF5» в BST), на клиенте разрезается на поля; она проходит клиентскую проверку до Run только когда разбивка даёт ожидаемое число полей команды **и** полученные глагол и аргументы образуют валидную команду — как в примере BST, где «insert», «5» дают и ожидаемое число полей, и валидную команду. Само по себе корректное число полей валидность не гарантирует. Сервер при этом по Go-семантике видит один токен «insert\uFEFF5» и отвергает сценарий как неизвестную команду: клиент мог пропустить то, что сервер отвергнет. Не все исторические формы команд после такого разреза проходят клиентскую проверку — здесь описан только случай, когда проходит.
- NEL U+0085 на клиенте не пробельный и приклеивается к токену: «push\u00855» клиент отвергнет как неизвестную операцию, хотя сервер по Go-семантике разделил бы строку на «push» и «5» и принял бы операцию. Сохранение прежнего поведения фронтенда делает такой серверно-валидный сценарий недоступным через UI: пользователь не сможет отправить команду, которую сервер принял бы.

Решение: Go-семантика — только у парсера Trie (клиент и сервер там совпадают); исторические парсеры остаются на JS-семантике, их перевод на Go-семантику — отдельное решение, не входящее в тикет 42.

## Considered Options

- **Семантический паритет только для Trie, исторические парсеры остаются на JS-семантике** (выбрано): прежние визуализации работают как раньше, Trie получает совпадающую клиент-серверную токенизацию.
- Глобальная унификация под Go-семантику — отклонено: молча изменило бы разбор прежних сценариев (BOM перестал бы отделять токен, NEL перестал бы быть частью токена) и нарушило бы требование тикета 42 о сохранении поведения старых визуализаций.
- Глобальная унификация под JS-семантику — отклонено: клиент пропускал бы формы, которые серверный парсер Trie разобрал бы иначе (BOM приклеился бы к токену на сервере), — ловить такие ошибки до Run было бы нельзя.
