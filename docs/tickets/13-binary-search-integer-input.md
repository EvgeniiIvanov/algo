# 13: Бинарный поиск — строгая проверка целых чисел во фронтенде

**What to build:** при вводе массива и искомого значения для бинарного поиска фронтенд принимает только числа в десятичном целочисленном формате, совместимом с серверным парсером. Некорректный формат (например, `2.0`, `1e2`, `0x10`) получает понятную ошибку до отправки Run, а не HTTP 400 после запроса.

**Blocked by:** 08 (стек сквозным срезом — сначала завершить изменения общей формы в `main.ts`).

**Status:** ready-for-agent

## Acceptance Criteria

- [ ] Парсер значений массива и target отвергает до отправки Run формы, не совместимые с серверным парсером: десятичную дробь (`2.0`), экспоненциальную (`1e2`), hex-запись (`0x10`), пустой ввод и пустые компоненты
- [ ] Допустимые десятичные целые принимаются по синтаксису серверного `strconv.Atoi` (необязательный знак, ведущие нули) в пределах безопасного целого `Number.MAX_SAFE_INTEGER`; значения за пределами — осознанное отклонение, а не молчаливое округление (см. Notes)
- [ ] Сообщение об ошибке ввода остаётся понятным и локализованным на русском; при ошибке запрос Run не отправляется
- [ ] Фронтенд-тесты покрывают допустимые и отклоняемые формы ввода для массива и target
- [ ] Существующие сценарии бинарного поиска и стека остаются рабочими; frontend lint/test/build и `go test ./...` зелёные

## Notes

- Синтаксис совпадает с `strconv.Atoi` (необязательный знак, только десятичные цифры), но **полного int64-паритета нет**: значение за пределами `Number.MAX_SAFE_INTEGER` клиент отклоняет человекочитаемой ошибкой, потому что `Number` не представляет такие числа точно (по итогам принятого ревью тикета 08). Значения, влезающие в int64, но вышедшие за безопасное целое, сервер принял бы, а браузер — нет; это неустранимое ограничение клиента, а не упущение.
- Парсинг массива и target переезжает из `main.ts` в `src/binarysearch.ts` — шов фронта, чтобы было что тестировать (как `scenario.ts` для стека и `sse.ts` для кадров).
