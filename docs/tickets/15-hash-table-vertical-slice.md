# 15: Хеш-таблица с коллизиями сквозным срезом

**What to build:** учащийся может создать таблицу с заданным числом корзин, выполнить сценарий `put`/`get`/`delete` и увидеть, как разные ключи попадают в одну корзину и разрешают коллизию цепочкой. Реализация повторяет решения модуля в `docs/SPEC.md` и использует существующие швы библиотеки, визуализатора и фронтенда.

**Blocked by:** None (can start immediately).

**Status:** in-progress

Спека: `docs/SPEC.md`, секция модуля «Хеш-таблицы с коллизиями».

`автор-черновик: человек` — перед реализацией пользователь пишет черновик HashTable в `algorithms/structures`; агент дорабатывает его по находкам ревью и не переписывает молча.

## Acceptance Criteria

- [x] В `algorithms/structures` есть HashTable с созданием таблицы, `Put`, `Get`, `Delete` и `Len` по утверждённой спеке: целочисленные ключи и значения, фиксированное положительное число корзин, разрешение коллизий методом цепочек; ключи с одинаковым bucket-индексом остаются доступны.
- [x] Индекс корзины вычисляется по modulo с нормализацией отрицательных остатков; повторный `Put` обновляет значение существующего ключа без увеличения `Len`; `Get` и `Delete` возвращают различимый результат для попадания и промаха; удаление одного элемента не повреждает остальные записи цепочки. Некорректный размер при создании возвращает ошибку, не панику.
- [x] Библиотечный API работает в quiet mode; типизированные события через общий Emitter показывают выбранную корзину, визиты записей и вставку/обновление/удаление/результат поиска. Тесты публичного поведения покрывают коллизии, отрицательные ключи, обновление, промахи, удаление из цепочки и длину; emitter-шпион — известную последовательность событий.
- [x] Кадры нового `kind="hash-table"` — самодостаточные снимки всех корзин и записей цепочек с подсветкой выбранной корзины и посещённых/изменённых записей; удалённая на шаге запись показывается надгробием (ключ, значение, бывшая позиция) — роль `removed` на живых записях не используется, кадры удаления не добавляются сверх одного кадра на событие HashRemove. Кадры содержат операцию и пояснение на русском. Контракты существующих `array` и `structure` кадров не меняются.
- [x] Маршрут `GET /api/run/hash-table` принимает параметры `buckets` и `script`; `script` содержит операции `put <key> <value>`, `get <key>`, `delete <key>` по одной на строку. Парсер отвергает неизвестные команды, неверное число аргументов и некорректные целые до начала SSE; промахи `get`/`delete` являются штатными шагами, а не ошибками запроса.
- [x] Фронтенд позволяет задать число корзин и сценарий, зеркально валидирует ввод до Run и рисует пустые корзины, цепочки с коллизиями, визиты, попадания, промахи, обновления и удаления. Тесты публичного frontend-шва покрывают сценарии и оба типа результата рендера; существующие визуализации продолжают работать.
- [x] Safety limits одинаковы на сервере и фронтенде: 1–100 корзин, не более 100 одновременно хранимых записей и не более 500 операций в одном Run. Границы проверяются тестами точно: 500 операций принимаются, 501-я отвергается до Run. Пустой сценарий и сценарий, превышающий любой лимит, отвергаются до отправки Run/начала SSE. При принятой гранулярности событий эти пределы гарантируют не более 51 001 кадра за Run; отдельное runtime-отсечение SSE не добавляется.
- [x] Интеграционный тест маршрута сравнивает ожидаемые SSE-кадры на сценарии с коллизией, попаданием, промахом и удалением из цепочки.
- [x] `go build ./...`, `go vet ./...`, `go test ./...`, Go lint, а также frontend lint/test/build проходят.
