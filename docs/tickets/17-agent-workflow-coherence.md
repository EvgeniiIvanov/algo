# 17: Согласование агентного процесса (OpenCode-only)

**What to build:** процессная документация, профили агентов и скиллы должны описывать один согласованный сценарий работы: автоматизация только в OpenCode (оркестратор строго не кодит, реализация — субагентом `implementor` в worktree тикета); учебный черновик пользователя — явный блокирующий чекпойнт Ч2.5; ревью — две независимые оси двумя свежими дочерними сеансами `reviewer`; git-политика (локальные коммиты после проверок, push только с одобрением, мерж и интеграция — человек, чистка worktree после мержа). Без правок исходников приложения.

**Blocked by:** — (процессный тикет, без зависимостей).

**Status:** done

**автор-черновик:** не применим (тикет не библиотечный — код/структура не затрагиваются).

## Acceptance Criteria

- [x] `AGENTS.md`, `docs/WORKFLOWS.md` и профили `.opencode/agents/*.md` согласованы: OpenCode — единственный хост агентов, VS Code — только место для черновиков пользователя; контекст задачи — всегда `AGENTS.md` + `docs/WORKFLOWS.md`, тикет/spec и только релевантные ADR/глоссарий. Все четыре профиля ведутся на английском.
- [x] Оркестратор строго не реализует код: вся реализация делегируется субагенту `implementor` в worktree тикета; спавнить можно только `implementor`, `reviewer`, `tester` — нативное правило `subagent` в V2-схеме `permissions` (deny `*`, allow трёх названных).
- [x] Ч2.5 (черновик алгоритма/структуры пишет пользователь) — явный блокирующий чекпойнт: реализация библиотечного тикета не стартует без черновика.
- [x] Тесты пишет `implementor`; `tester` — необязательная read-only риск-оценка, не автор тестов.
- [x] Ревью: две независимые оси Standards + Spec двумя параллельными свежими дочерними сеансами субагента `reviewer` (read-only); источники Spec-оси локальные (`docs/tickets/`, `docs/SPEC.md`), без требования `docs/agents/issue-tracker.md`.
- [x] Жизненный цикл worktree → реализация → ревью → мерж → чистка явно описан как повторяющийся на каждый тикет, а не раз на модуль; чистка после подтверждённого мержа выполняется оркестратором из основной папки с одобрением пользователя, без force и без удаления удалённых веток.
- [x] Git-policy: имплементор проверяет свою ветку `ticket/...` инструкцией (не негативным permission), коммитит локально после проверок; push — с одобрением (нативный fallback `shell *` → `ask`), мерж в `main` и обычное удаление локальных веток — запрет инструкцией; нативный deny зашит для прямых форм force push и force-удаления веток — то есть для явно заматченных direct-форм команд (произвольные shell-обёртки — не песочница).
- [x] Нативные permissions: у `reviewer` и `tester` запрещён edit и узкий read-only allowlist shell-команд (инспекционные git-команды, включая `git rev-parse`; для `tester` — точная команда `make test`).
- [x] Схема permissions V2: во всех четырёх профилях убраны legacy-шапки (`permission`/`bash`/`task`, ранее также `temperature`) и используются упорядоченные записи `{action, resource, effect}` с действиями `shell`/`subagent`; общие read-only инспекционные git-правила централизованы в `opencode.json`, а deny-правила стоят после более широких `ask` (last-match-wins).
- [x] Deny для force push покрывает явно заматченные прямые формы в любой позиции (`--force*`, короткий `-f` с кластерами, `+рефспек`, включая `git -C <путь> push ...`), а также прямые формы удаления веток на origin (`--delete`, короткий `-d` с кластерами, `:`-рефспеки, `--mirror`, `--prune`); deny для `git worktree remove` покрывает `--force`/`-f` и короткие кластеры; у оркестратора `git worktree remove` и `git branch -d` — `ask`, push — `ask`, прямые формы удаления веток на origin запрещены нативно. Матчинг — по тексту разобранных сегментов команды; это не песочница для произвольных обёрток, непокрытые команды требуют одобрения OpenCode.
- [x] `git rev-parse *` добавлен в общий read-only инспекционный allowlist (валидация фиксированной точки ревью не требует промпта); различие «инструкция vs нативный permission» для мержа/удаления веток имплементора отражено в AGENTS.md, тикете и профилях.
- [x] Скилл `code-review` согласован с репозиторием: фиксированная точка по умолчанию `main...HEAD` (если пользователь не задал иную), локальные источники тикета/spec, два параллельных свежих `reviewer`-ребёнка с отдельными промптами осей, без блокировки на issue-tracker.
- [x] Скилл `implement` согласован с git-политикой (локальный коммит после проверок на своей ветке тикета; push только с одобрением; мерж в `main` — никогда); скилл `implement-spec` не тронут и явно помечен вне канонического потока репозитория.
- [x] Правка по второму ревью (пользователь выбрал «только критические»): shell-allowы `implementor` сужены с префиксов `go *`/`make *`/`pnpm *` до точного списка команд проекта (цели make из Makefile, скрипты pnpm из `visual/frontend/package.json`, `go build/vet/test ./...`, `golangci-lint run ./...`, `git add`/`git commit`); `pnpm exec ...`, `go run`, dev-серверы, фокус-тесты и произвольные make-цели не подпадают под allow и запрашивают одобрение. Общие deny-правила V2 расширены: короткие кластеры force (`-fv`, `-df`/`-fd`, без ложного срабатывания на `--follow-tags`), `--mirror`/`--prune`, прямые формы `git -C <путь> push ...` и force-удаления веток через `git -C`. Язык документации уточнён: нативные deny работают для явно заматченных прямых форм команд; glob-матчинг — не песочница для произвольных обёрток, непокрытые команды требуют одобрения OpenCode через fallback `shell *` → `ask`.

## Правки по итогам второго ревью (объём: только критические)

- Исправлен обход shared Git-denies через широкие префиксы `pnpm *` / `make *` / `go *` в профиле `implementor` (пример обхода: `pnpm exec git push --force` — теперь сегмент не совпадает ни с одним allow и проходит через `ask`).
- Расширены общие deny-правила (`opencode.json`): кластеры коротких флагов force/delete, `--mirror`/`--prune`, варианты `git -C <путь>` для push, force-удаления веток (`-D`, долгое `--delete --force`, кластеры `-df`/`-fd`) и force-формы `git worktree remove` (включая `git -C`). Обычный локальный `git branch -d` остаётся вне нативного deny (у оркестратора — `ask`, у имплементора — инструкция).
- Формулировки в AGENTS.md, тикете и профилях уточнены: нативные deny применяются к явно заматченным прямым формам; shell-матчинг не является песочницей; все непокрытые команды идут через одобрение OpenCode (`shell *` → `ask`).
- Два минорных замечания ревью оставлены без изменений решением пользователя: расхождение слов в prose `reviewer`/`tester` про `git rev-parse`, и сохранение нативного запрета `git worktree list` (и прочих worktree-команд) у `implementor`.
