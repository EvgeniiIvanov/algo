# 23: Шаг очистки бэклога между модулями

**What to build:** процессный тикет: по ходу модулей накапливаются мелкие низкоприоритетные улучшения и рефакторинг, для которых нет места — они теряются в переписке или мешают сфокусироваться на модуле, а завершённый модуль сразу сменяется следующим. Вводим `docs/BACKLOG.md` — короткий человекочитаемый список таких заметок — и фиксируем в `docs/WORKFLOWS.md` отдельный шаг очистки бэклога после каждого завершённого учебного модуля, до старта следующего. Без правок исходников приложения.

**Blocked by:** — (процессный тикет, без зависимостей).

**Status:** in-progress

## Acceptance Criteria

- [ ] `docs/BACKLOG.md` создан: короткий человекочитаемый список низкоприоритетных улучшений кода/рефакторинга, замеченных по ходу работы. Формат записи — одна строка: область → улучшение → зачем; без статусов и полноценных планов. Баги (поток C) и новые фичи в список не попадают.
- [ ] `docs/WORKFLOWS.md` однозначно разводит завершение учебного модуля (отметка в `PROGRESS.md`) и отдельный шаг очистки бэклога: шаг выполняется после каждого завершённого модуля и до старта следующего; он не входит в модуль и не влияет на отметку его учебного контента в `PROGRESS.md`.
- [ ] Правило разбора зафиксировано: каждая запись получает решение — реализовать (поток D; связанные мелкие улучшения можно группировать в один тикет, независимые — отдельные тикеты), отбросить или превратить в обычный запланированный тикет; разобранные записи удаляются из `docs/BACKLOG.md`, нерешённых заметок не копим.
- [ ] Правки — только документация/процесс: `PROGRESS.md`, `GLOSSARY.md`, `docs/SPEC.md` и исходники приложения не затрагиваются.
