# 29: Триаж friction-лога и приоритет процессных тикетов

**What to build:** процессный тикет: трение процесса сейчас фиксируется в `docs/FRICTION_LOG.md`, но разбирается только на шаге очистки бэклога между модулями — неудобство, замеченное по ходу работы, может ждать неделями и даже блокировать текущую работу. Договариваемся о времени реакции и приоритете: новую friction-запись триажим сразу при замечании; блокирующее или повторяющееся трение оформляется приоритетным процессным тикетом, который берётся в работу и доводится до выполнения до начала обычных задач бэклога (разбирать и планировать их до того можно); активную работу прерываем только при реальной блокировке, в остальных случаях решение принимается на безопасной границе; если связанный тикет завершён, а трение осталось — запись триажится повторно (follow-up тикет или `rejected`). Заодно уточняется фактическое описание allowlist в существующей записи лога (разрешены проверочные цели `Makefile` и только frontend-скрипты `lint`/`test`/`build`, не «все Makefile-цели/package scripts») и согласуются статусы записей (`open` / `fixed` / `rejected`). Процессные тикеты идут по обычному циклу потока D; Ч2.5 применим только к библиотечным черновикам. Без правок исходников приложения.

**Blocked by:** — (процессный тикет, без зависимостей).

**Status:** in-progress

**автор-черновик:** не применим (тикет процессный — исходники приложения не затрагиваются).

## Acceptance Criteria

- [ ] `docs/FRICTION_LOG.md`: существующая запись о allowlist описывает фактическое состояние — разрешены прямые команды проверки (`go build`/`go vet`/`go test`/`go test -race` с `./...`, `gofmt -l quiz`, `golangci-lint run ./...`), проверочные цели `Makefile` и только frontend-скрипты `lint`/`test`/`build` (плюс `pnpm install --frozen-lockfile`); не утверждается, что разрешены все Makefile-цели или package scripts; указано, что runtime-цели Makefile (`run-api`, `run-frontend`, `run-quiz`) и скрипты `pnpm dev` / `preview` / `test:watch` в allowlist не входят. Историческая запись и её смысл сохранены. Точность сверена с профилем `.opencode/agents/implementor.md`.
- [ ] `docs/FRICTION_LOG.md`: нет противоречия между «запись не привязана к тикетам» и требованием указывать процессный тикет: запись — наблюдение о процессе, а не план работы; правило ссылки и остальные операционные детали статуса — каноничны в пункте «Статусы записи» самого лога.
- [ ] Статусы friction-записей согласованы и не переводятся: `open` / `fixed` / `rejected`; описания — на русском, идентификаторы статусов — английские. Смысл статусов: `open` — трение ещё не устранено (ожидает решения либо выполнения связанного тикета, при заведённом тикете запись остаётся `open` со ссылкой до его выполнения; не сводится только к ожиданию решения); `fixed` — только после фактического устранения трения, со ссылкой на коммит/файл; `rejected` — дальнейшие действия по записи прекращены с зафиксированной причиной: либо трение решено не устранять (и тикет не заводится), либо после завершившегося тикета решено не заводить follow-up. Записи `fixed`/`rejected` остаются в логе как история решений.
- [ ] `docs/FRICTION_LOG.md`: шаблон строки правил содержит обязательный статус (`где → что мешало → предлагаемое исправление (если есть) → статус`).
- [ ] `docs/WORKFLOWS.md`: опечатка `отрыто` исправлена; описан немедленный триаж новой friction-записи по ходу любой работы; единственное каноническое правило приоритета — приоритетный процессный тикет (цикл потока D) берётся в работу и доводится до выполнения до начала обычных задач бэклога (разбирать и планировать их до того можно): неблокирующее повторяющееся трение — тикет на ближайшей безопасной границе, активная работа прерывается только при реальной блокировке; грамматической конструкции «не только …, а …» в описании приоритета нет; числовая система приоритетов и новые чекпойнты не вводятся.
- [ ] `docs/WORKFLOWS.md`: описаны оба исхода завершённого связанного процессного тикета: трение устранено — запись закрывается `fixed` со ссылкой на коммит/файл; трение осталось (правка не помогла или вскрылось новое) — запись немедленно триажится повторно: follow-up процессный тикет либо `rejected` с причиной; запись не остаётся бесконечно `open` без следующего решения.
- [ ] `docs/WORKFLOWS.md`: на шаге очистки бэклога сначала — friction-триаж и решение по каждой открытой записи, затем обычный разбор `BACKLOG.md`. Записи со связанным незавершённым процессным тикетом уже имеют решение: остаются `open` со ссылкой на тикет, отдельное новое решение по ним не требуется, приоритет их выполнения — канон в разделе «Friction-лог». Открытые записи без связанного активного тикета получают решение на шаге: заведён и указан процессный тикет, либо `rejected` с причиной, либо `fixed` по правилам статусов лога, если трение устранено; после шага единственные оставшиеся `open`-записи — записи со связанным активным процессным тикетом. Записи в статусах `fixed`/`rejected` шаг не затрагивает — они остаются историей; серверные детали статусов не дублируются — канон статусов в `docs/FRICTION_LOG.md`. Гарантия приоритета — «начало выполнения обычных задач бэклога только после выполнения приоритетного процессного тикета» — сформулирована канонически один раз в разделе «Friction-лог»; шаг ссылается на неё кратко, операционный порядок шага (friction-триаж перед разбором бэклога) не смешивается с формулировкой гарантии. Дубли этого шага с разделом «Friction-лог: фиксация и триаж» убраны.
- [ ] `docs/WORKFLOWS.md`: в описании потока D и/или таблице типов работ указано, что процессные и документационные тикеты идут по обычному тикетному циклу потока D, при этом Ч2.5 применим только к библиотечным черновикам; новых чекпойнтов не добавлено.
