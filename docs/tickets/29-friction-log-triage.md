# 29: Триаж friction-лога и приоритет процессных задач

**What to build:** процессный тикет: трение процесса сейчас фиксируется в `docs/FRICTION_LOG.md`, но разбирается только на шаге очистки бэклога между модулями — неудобство, замеченное по ходу работы, может ждать неделями и даже блокировать текущую работу. Договариваемся о времени реакции и приоритете: новую friction-запись триажим сразу при замечании; блокирующее или повторяющееся трение оформляется приоритетной процессной задачей и решается раньше обычных задач бэклога; активную работу прерываем только при реальной блокировке, в остальных случаях решение принимается на безопасной границе. Заодно уточняется фактическое описание allowlist в существующей записи лога (разрешены проверочные цели `Makefile` и только frontend-скрипты `lint`/`test`/`build`, не «все Makefile-цели/package scripts») и согласуются статусы записей (`open` / `fixed` / `rejected`). Без правок исходников приложения.

**Blocked by:** — (процессный тикет, без зависимостей).

**Status:** in-progress

**автор-черновик:** не применим (тикет процессный — исходники приложения не затрагиваются).

## Acceptance Criteria

- [ ] `docs/FRICTION_LOG.md`: существующая запись о allowlist описывает фактическое состояние — разрешены проверочные цели `Makefile` и только frontend-скрипты `lint`/`test`/`build` (плюс `pnpm install --frozen-lockfile`); не утверждается, что разрешены все Makefile-цели или package scripts; указано, что runtime-цели (`make run-*`) и `pnpm dev` / `preview` / `test:watch` в allowlist не входят. Историческая запись и её смысл сохранены.
- [ ] Статусы friction-записей согласованы и не переводятся: `open` / `fixed` / `rejected`; описания — на русском, идентификаторы статусов — английские (`fixed` не переводится как «исправлено»).
- [ ] `docs/WORKFLOWS.md`: опечатка `отрыто` исправлена; описан немедленный триаж новой friction-записи по ходу любой работы; критерии приоритета: блокирующее или повторяющееся трение оформляется приоритетной процессной задачей (тикет потока D) и решается раньше обычных задач бэклога; активная работа прерывается только при реальной блокировке, в остальных случаях — на безопасной границе; разбор на границе модулей остаётся как проверка оставшихся открытых записей, а не единственное время реакции; числовая система приоритетов не вводится.
- [ ] Связь с процессными тикетами: из `docs/WORKFLOWS.md` и `docs/FRICTION_LOG.md` понятно, что приоритетное трение оформляется процессным тикетом, а запись лога остаётся `open` со ссылкой на тикет до его выполнения.
- [ ] `AGENTS.md`: агент при замечании трения фиксирует и триажит его по ходу работы — короткий указатель на правила в `docs/WORKFLOWS.md`, без дублирования подробного workflow.
- [ ] `GLOSSARY.md`: согласованность терминов проверена; краткое определение friction-лога добавлено рядом с Backlog без дублирования определений.
- [ ] Документация непротиворечива между собой и с фактическим allowlist в профиле `implementor` (`AGENTS.md`, `docs/WORKFLOWS.md`, `docs/FRICTION_LOG.md`, `docs/BACKLOG.md`, `GLOSSARY.md`, статусы существующих тикетов); русская грамматика и терминология выверены; правки — только документация/процесс: исходники приложения, `docs/SPEC.md` и `PROGRESS.md` не затрагиваются.
