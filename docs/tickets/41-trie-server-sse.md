# 41: Trie — сценарий, кадры и SSE

**What to build:** учащийся запускает сценарий операций над Trie и получает SSE-кадры с пошаговым обходом по rune и изменениями дерева.

**Blocked by:** 40 (нужны операции Trie и их типизированные события).

**Status:** planned

Спека: `docs/SPEC.md`, модуль «Trie: вставка, поиск, префиксы и удаление».

## Acceptance Criteria

- [ ] `GET /api/run/trie` принимает URL-кодированный `script`: по одной команде `insert W`, `search W`, `prefix W` или `delete W` на строку. Сценарий строит Trie с пустого корня; пустые строки и строки только из пробелов игнорируются; пустой или без-командный сценарий отвергается.
- [ ] Аргумент команды — один непустой Unicode-токен без пробелов. Некорректная команда, лишний или пустой аргумент, слово или префикс длиннее 100 rune и превышение лимитов отвергаются до начала SSE.
- [ ] Лимиты Run проверяются сервером до SSE: не более 500 команд, не более 100 rune в слове/префиксе, не более 100 живых rune-узлов (корень не считается). Лимит живых узлов применяется к пиковому размеру Trie — максимуму числа живых узлов по состоянию после каждой команды сценария, а не только к финальному; семантика одинакова у сервера и TS dry-run. Некорректный сценарий и превышение любого лимита дают ошибку без частично начатого потока.
- [ ] Гранулярность событий соответствует спеке: каждое реально посещённое/проверенное rune-ребро даёт не более одного события посещения (одно событие несёт и состояние ребра — переиспользование или создание, а на последней rune вставки/удаления — итоговое состояние terminal flag, и только когда оно меняется: дубликат вставки и промах удаления флаг не меняют; отдельного события terminal-mark нет), не более одного события на каждый pruning node и ровно одно событие результата на команду. Delete снимает terminal flag в последнем событии посещения. В визуальном Run событий pruning не более 100 на команду — следствие лимита длины входа в 100 rune. Верхняя граница потока — 500 × (100 rune-переходов + 100 pruning-узлов + 1 результат) + 1 стартовый кадр = 100 501 кадр; итоговое состояние terminal flag идёт последним событием посещения и отдельного события не создаёт.
- [ ] Повторная вставка и промахи `search`/`prefix`/`delete` остаются допустимыми шагами сценария с явным пояснением на русском.
- [ ] Frame Renderer строит исходный кадр и кадры по событиям алгоритма; каждый кадр — полный самодостаточный снимок `kind="trie"` с произвольным ветвлением, отметками конца слова, активным путём текущей операции, именем операции и пояснением на русском. Поле `result` — часть снимка Trie внутри `Frame.Data` (не поле верхнего Frame envelope): стартовый кадр и все промежуточные кадры посещения/pruning до события результата — ровно `result: null`; кадр результата операции — единственный кадр команды с заполненным `result`, одно значение закрытого множества `insert` / `already-existed`, `found` / `not-found`, `prefix-found` / `prefix-not-found`, `deleted` / `not-deleted`.
- [ ] Идентификаторы узлов в снимке `kind="trie"` — frame-local пути от корня по rune-меткам рёбер в каноническом кодировании: `root` для корня, далее по сегменту на rune — `U+` и шестнадцатеричный код rune в верхнем регистре минимальной ширины 4 (длиннее при необходимости), разделитель `/` (например, `root/U+043F/U+0440`), уникальные в пределах каждого кадра; обработчик не требует межкадровой стабильности и не переиспользует L/R-контракт бинарного `NodeID`.
- [ ] Снимки после вставки и удаления отражают изменённое дерево; pruning при удалении показывается кадрами, в которых ставшие ненужными узлы исчезают.
- [ ] Контракт существующего бинарного `kind="tree"` (обходы, BST) не меняется; общий SSE-транспорт и плеер не трогаются.
- [ ] SSE-интеграционные тесты проверяют сценарий со вставками с общим префиксом, точным поиском и промахом, проверкой префикса и удалением с pruning; тесты сверяют идентификаторы узлов и поле `result` снимков Trie внутри `Frame.Data` по контракту: `null` в стартовом и промежуточных кадрах посещения/pruning, значение закрытого множества только в кадре результата операции. Тесты покрывают каждый вариант закрытого множества `result` отдельным случаем, включая no-op-значения: повторный Insert → `already-existed`, промах Delete → `not-deleted`, промах prefix → `prefix-not-found`, со сверкой промежуточных `data.result: null` и финального enum. Сценарий с пиком живых rune-узлов >100 и финальным ≤100, игнорирование пустых строк/строк из пробелов и отказ от сценария без команд, а также отказ от некорректного сценария и лимитов проверяются до SSE.
- [ ] `go build ./...`, `go vet ./...`, `go test ./...` и `golangci-lint run ./...` проходят.
