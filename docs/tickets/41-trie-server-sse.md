# 41: Trie — сценарий, кадры и SSE

**What to build:** учащийся запускает сценарий операций над Trie и получает SSE-кадры с пошаговым обходом по rune и изменениями дерева.

**Blocked by:** 40 (нужны операции Trie и их типизированные события).

**Status:** planned

Спека: `docs/SPEC.md`, модуль «Trie: вставка, поиск, префиксы и удаление».

## Acceptance Criteria

- [ ] `GET /api/run/trie` принимает URL-кодированный `script`: по одной команде `insert W`, `search W`, `prefix W` или `delete W` на строку. Сценарий строит Trie с пустого корня; пустые строки и строки только из пробелов игнорируются; пустой или без-командный сценарий отвергается.
- [ ] Аргумент команды — один непустой Unicode-токен без пробелов из валидного UTF-8 (последовательность Unicode scalar values). Некорректная команда, лишний или пустой аргумент, слово или префикс длиннее 100 rune и превышение лимитов отвергаются до начала SSE; невалидный UTF-8 — сыро закодированный невалидный байт (например, `%FF`) — отвергается до SSE; граничный тест лимита длины изолирован от лимита живых узлов: `search` с аргументом ровно из 100 повторных `😀` в пустом Trie принимается и доводится до кадра результата операции `not-found` без создания узлов, аргумент из 101 `😀` отвергается до SSE (rune считается по Unicode scalar values, не по UTF-8 байтам).
- [ ] Лимиты Run проверяются сервером до SSE: не более 500 команд, не более 100 rune в слове/префиксе, не более 100 живых rune-узлов (корень не считается). Лимит живых узлов применяется к пиковому размеру Trie — максимуму числа живых узлов по состоянию после каждой команды сценария, а не только к финальному; семантика одинакова у сервера и TS dry-run. Некорректный сценарий и превышение любого лимита дают ошибку без частично начатого потока.
- [ ] Гранулярность событий соответствует спеке: каждое rune-обращение даёт не более одного события посещения/проверки (состояние ребра: `reused` для существующего, `created` для нового, создаваемого вставкой; вставка всегда проверяет все rune и после создания отсутствующего ребра с состоянием `created` продолжает обход; ограничение «до первой отсутствующей rune включительно» относится только к попыткам `search`/`prefix`/`delete` пройти отсутствующее ребро — последнее событие проверки несёт состояние `missing` и проверяемую rune, без создания узла; на последней rune вставки/удаления — итоговое состояние флага конца слова, и только когда оно меняется: повторная вставка и промах удаления флаг не меняют; отдельного события отметки конца слова нет), не более одного события на каждый узел pruning и ровно одно событие результата на валидную команду. Удаление снимает флаг конца слова в последнем событии посещения. Событие проверки отсутствующего ребра входит в не более 100 rune-переходов и проверок на команду и не считается сверх длины. В визуальном Run событий pruning не более 100 на команду — следствие лимита длины входа в 100 rune. Верхняя граница потока — 500 × (100 rune-переходов и проверок + 100 узлов pruning + 1 результат) + 1 стартовый кадр = 100 501 кадр; итоговое состояние флага конца слова идёт последним событием посещения и отдельного события не создаёт.
- [ ] Повторная вставка и промахи `search`/`prefix`/`delete` остаются допустимыми шагами сценария с явным пояснением на русском.
- [ ] Frame Renderer строит исходный кадр и кадры по событиям алгоритма; каждый кадр — полный самодостаточный снимок `kind="trie"` с произвольным ветвлением, отметками конца слова, активным путём текущей операции, именем операции и пояснением на русском. Поле `edgeCheck` — часть снимка Trie внутри `Frame.Data`: в каждом кадре посещения/проверки rune — при состояниях `reused`, `created` и `missing` — объект `{ rune: <JSON-строка ровно из одной rune (Unicode scalar value), не числовой код>, state: "reused" | "created" | "missing" }`; во всех остальных кадрах — стартовом, промежуточных pruning и в кадре результата операции — ровно `edgeCheck: null`. При `reused`/`created` активный путь доходит до существующего/созданного потомка; при `missing` активный путь содержит только существующие узлы — до родителя отсутствующего ребра, а отсутствующий потомок не добавляется в топологию и не имеет идентификатора узла; попытка видна через `edgeCheck.rune` отдельно. Поле `result` — часть снимка Trie внутри `Frame.Data` (не поле верхнего Frame envelope): стартовый кадр и все промежуточные кадры посещения/проверки/pruning до события результата — ровно `result: null`; кадр результата операции — единственный кадр команды с заполненным `result`, одно значение закрытого множества `insert` / `already-existed`, `found` / `not-found`, `prefix-found` / `prefix-not-found`, `deleted` / `not-deleted`.
- [ ] Идентификаторы узлов в снимке `kind="trie"` — frame-local пути от корня по rune-меткам рёбер в каноническом кодировании: `root` для корня, далее по сегменту на rune — `U+` и шестнадцатеричный код rune в верхнем регистре минимальной ширины 4 (длиннее при необходимости), разделитель `/` (например, `root/U+043F/U+0440`), уникальные в пределах каждого кадра; обработчик не требует межкадровой стабильности и не переиспользует L/R-контракт бинарного `NodeID`.
- [ ] Снимки после вставки и удаления отражают изменённое дерево; pruning при удалении показывается кадрами, в которых ставшие ненужными узлы исчезают.
- [ ] Контракт существующего бинарного `kind="tree"` (обходы, BST) не меняется; общий SSE-транспорт и плеер не трогаются.
- [ ] SSE-интеграционные тесты проверяют сценарий со вставками с общим префиксом, точным поиском и промахом, проверкой префикса и удалением с pruning; тесты сверяют идентификаторы узлов и поле `result` снимков Trie внутри `Frame.Data` по контракту: `null` в стартовом и промежуточных кадрах посещения/pruning, значение закрытого множества только в кадре результата операции. Тесты покрывают каждый вариант закрытого множества `result` отдельным случаем, включая no-op-значения: повторный Insert → `already-existed`, промах Delete → `not-deleted`, промах prefix → `prefix-not-found`, со сверкой промежуточных `data.result: null` и финального enum; no-op-сценарии включают промахи по отсутствующему ребру (search, prefix, delete) и существующий путь, конечный узел которого не отмечен как конец слова (search, delete), со сверкой событий посещения/проверки и события результата; кадры сверяются по полю `edgeCheck` — одно имя и одна форма в JSON между бэкендом и фронтом: `edgeCheck: null` в стартовом, промежуточных pruning и кадре результата операции (тест-ассерты на каждый случай), объект `{ rune: <JSON-строка ровно из одной rune>, state }` в каждом кадре посещения/проверки — включая символы вне BMP: JSON-строка `edgeCheck.rune` для `😀` — ровно `😀`, а идентификатор узла — `root/U+1F600` (hex-код rune, не surrogate-половина `U+D83D`); синонимичного поля `status` нет; состояния покрываются тестами: `created` при вставке в пустой Trie, `reused` при вставке второго слова по общему префиксу, `missing` при промахах — при `missing` активный путь содержит только существующие узлы до родителя отсутствующего ребра, а отсутствующий потомок отсутствует в топологии и не имеет идентификатора узла; `data.result` остаётся `null` до кадра результата операции. Пустой аргумент команды отвергается до Run, поэтому empty-API случаи проверяются emitter-тестами библиотеки (тикет 40), а не сценарием. Сценарий с пиком живых rune-узлов >100 и финальным ≤100, игнорирование пустых строк/строк из пробелов и отказ от сценария без команд, а также отказ от некорректного сценария и лимитов проверяются до SSE; отдельно — тест невалидного UTF-8: сыро закодированный невалидный байт (`%FF` в аргументе) отвергается до SSE без частично начатого потока, и граничный тест длины: `search` из 100 повторных `😀` в пустом Trie доводится до кадра результата операции `not-found` без создания узлов, из 101 — отвергается до SSE.
