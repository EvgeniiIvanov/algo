# 42: Trie — фронтенд сценария и кадров

**What to build:** учащийся задаёт сценарий Trie во фронтенде, запускает его и видит обход по rune, отметки конца слова и изменённое дерево на каждом кадре.

**Blocked by:** 41 (нужен контракт серверного Run и снимков `kind="trie"`).

**Status:** planned

Спека: `docs/SPEC.md`, модуль «Trie: вставка, поиск, префиксы и удаление».

## Acceptance Criteria

- [ ] Во фронтенде доступен сценарий Trie с командами `insert W`, `search W`, `prefix W`, `delete W`; стартовое дерево пустое.
- [ ] Публичная проверка входа зеркалирует серверные правила: один непустой Unicode-токен без пробелов, до 100 rune в слове/префиксе, до 500 команд; пустые строки и строки только из пробелов игнорируются, сценарий без единой команды отвергается; Run URL корректно кодирует `script` для `GET /api/run/trie` и совпадает с серверным контрактом.
- [ ] Публичная симуляция сценария (dry-run) в TS считает пиковое число живых rune-узлов до Run (корень не считается) — максимум по состоянию после каждой команды, а не только финальное — и зеркально проверяет лимит в 100 живых rune-узлов той же семантикой, что и сервер до SSE; превышение лимита и иные нарушения отвергаются до отправки Run.
- [ ] Кадры `kind="trie"` принимаются и рендерятся: произвольное ветвление, отметки конца слова и активный путь видны в каждом снимке; поле `edgeCheck` — часть снимка Trie внутри `Frame.Data`: в каждом кадре посещения/проверки rune — при состояниях `reused`, `created` и `missing` — объект `{ rune: <JSON-строка ровно из одной Unicode rune/code point>, state: "reused" | "created" | "missing" }`; во всех остальных кадрах — стартовом, промежуточных pruning и в кадре результата операции — ровно `edgeCheck: null`; форма та же, что у бэкенда. При `missing` активный путь рендерится только из существующих узлов — до родителя отсутствующего ребра, а отсутствующий потомок отсутствует в топологии и не имеет идентификатора узла. Поле `result` — часть снимка Trie внутри `Frame.Data` (не envelope кадра): ровно `null` в стартовом и промежуточных traversal/pruning снимках; кадр результата операции — единственный снимок команды с заполненным `result`, одно значение закрытого множества (`insert` / `already-existed`, `found` / `not-found`, `prefix-found` / `prefix-not-found`, `deleted` / `not-deleted`) с итогом шага.
- [ ] Рендер работает с идентификаторами узлов — frame-local путями по rune-меткам рёбер в каноническом кодировании (`root` для корня, далее по сегменту на rune — `U+` и hex-код rune в верхнем регистре минимальной ширины 4, разделитель `/`, например `root/U+043F/U+0440`) — без предположения о межкадровой стабильности и без L/R-контракта бинарного `NodeID`.
- [ ] Публичные тесты проверяют допустимый/недопустимый сценарий (включая игнорирование пустых строк/строк из пробелов и отказ сценария без команд), dry-run пикового лимита живых узлов, включая сценарий с пиком >100 и финалом ≤100, построение URL и рендер идентификаторов и `result` (`null` на промежуточных снимках, enum только в кадре результата операции); рендер проверяется на каждом варианте закрытого множества `result`, включая no-op-значения: повторный Insert → `already-existed`, промах Delete → `not-deleted`, промах prefix → `prefix-not-found`; на кадрах no-op-сценариев — промахи по отсутствующему ребру (search, prefix, delete) и существующий путь без отметки конца слова (search, delete) — со сверкой активного пути из существующих узлов, поля `edgeCheck` (`edgeCheck: null` в стартовых/pruning/result-кадрах, `{ rune: <строка ровно из одной rune>, state }` в кадрах посещения/проверки, включая состояния `created`, `reused` и `missing`) и `result: null` до кадра результата операции; и на кадрах вставки с общим префиксом, точного поиска и промаха, проверки префикса и удаления с pruning.
- [ ] UI и фронтенд-тесты прежних визуализаций (обходы, BST) продолжают работать без изменения их поведения; контракт `kind="tree"` не меняется.
- [ ] `pnpm install --frozen-lockfile`, `pnpm lint`, `pnpm test` и `pnpm build` проходят.
